# P2 设计草案 — 写入侧槽位化抽提（原文不截断）

> 状态：**草案，未获批准，未动任何写入代码**（2026-10-19）
> 前置：P1 读路径（关键词通道 + 融合）已上线并验证（见 `伯仕记忆系统v7.1_检索融合技术文档.md`）
> 本文件只做设计，等你拍板后才改 `plugins/boshi/__init__.py`

## 1. 为什么必须做（实测基数）

| 项 | 数字 | 来源 |
|---|---|---|
| `assistant_conclusion` 总数 | 1840 | `select count(*) from boshi.memories where topic='assistant_conclusion'` |
| 被 `…` 截断 | 1124（61%） | `right(content,1)='…'` |
| 平均长度 / 最长 | 691 / 4075 | 最长那条丢了 3275 字 |
| `conversation` 截断 | 270 / 3299（8%） | ≤500 字截断 |
| `boshi.memories` 体积 | 84 MB（含 1024 维向量） | `pg_total_relation_size` |

截断不只是"少存字"，它制造**假匹配**：`[2026-07-02] DeepSeek-R1…--tensor-s` 这种半截 token
会被 BM25 的 substring 规则命中，是 `tensor-split 显存` 榜首一度跑偏的直接原因之一。
搜索质量的天花板在写入侧。

**原文可回填**：Hermes `state.db` 里 `messages` 表仍有 34,718 条 assistant 消息
（其中 >800 字 2033 条，最长 28,892 字，合计 593 万字符）；用 boshi 截断行前 60 字做前缀精确匹配，
**200 条抽样命中 187 条（94%）**。→ 历史截断可回填。

## 2. 方案（推荐路线）

### 2.1 抽提器：零模型规则抽提

理由：可复现、零 token、不可能幻觉，与你"不用模型生成内容"的一贯原则一致。
原型 `p2_dryrun2.py` 在 1840 条真实数据上的覆盖率：

```
statement             1834  99.7%
versions               975  53.0%
numbers                777  42.2%
files                  464  25.2%
boundary_envs          454  24.7%
reusable_experience    395  21.5%
decisions              326  17.7%
open_questions         274  14.9%
flags                  260  14.1%
ports                   67   3.6%
commands                21   1.1%
零槽位 230 条（12%）；≥5 个槽位 90 条（5%）
```

规则（全部正则/行级，无模型）：

- `files`：盘符路径 `(?<![A-Za-z0-9_.])[A-Za-z]:[\\/]…`（负向断言挡掉 `https://` 里的 `s:/`）、
  POSIX 绝对路径、相对路径 `a/b/c.py`
- `commands`：行首 `python|pip|uv|git|curl|wget|netstat|schtasks|nvidia-smi|llama-server|ollama|psql|docker|node|npm`
- `flags`：`--flag`；`numbers`：`\d+(\.\d+)?\s?(GB|MB|ms|tok/s|s|°C|%)`；`ports`：`ip:port`
- `versions`：排除 IP 片段与带单位的数字（`47.6 MB` 的 47.6 不算版本）
- 句子级四类：`decisions`（决定/改为/选用/结论是…）、`open_questions`（待/未合并/还没…）、
  `reusable_experience`（铁律/教训/坑/注意/必须…）、`boundary_envs`（端口/显存/CUDA/Python…）
- markdown 表格行先剔除（否则 `| 项目 | 版本 |` 会污染 `boundary_envs`）

已知局限：`commands` 覆盖率 1.1%（大多数命令在正文行内而非行首）、`decisions` 会抓到
"建议换成还能用的：" 这种半句。**不追求召回率**，宁可少抓不可抓错。

### 2.2 存储：原文全存 + 槽位列

```sql
ALTER TABLE boshi.memories ADD COLUMN slots jsonb;       -- 抽提结果
ALTER TABLE boshi.memories  ADD COLUMN raw_len int;      -- 原文长度（对比 content 长度可判断是否完整）
```

- `content` 存**全文**，不再 `[:800] + "…"`（`plugins/boshi/__init__.py:645-646`）
- 增量成本：84MB 表里 content 只占小部分，2033 条 >800 字原文合计约 400 万字符 ≈ 8MB（UTF-8 中文 3 字节）
- `slots` 为空表示未抽提（历史行、或抽提失败），检索行为与今天一致 → 向后兼容

### 2.3 检索侧配合

- 槽位记录带 `slots` 时，`statement` 与 `slots` 的文本一起进关键词索引（P1 的进程内 BM25）
- 原文（长文本）不参与 BM25 全文扫描，避免半截 token 假匹配；只在命中后作为展开层返回
- 排序：槽位命中的记录 > 原文里偶然命中的记录

### 2.4 回填历史（可选，需单独批准）

1. 取 `right(content,1)='…'` 的 1124 条
2. 用前 60 字在 `state.db` `messages`（role='assistant'）精确前缀匹配
3. 命中则覆盖 `content` 为原文、写 `raw_len`、跑抽提写 `slots`
4. 未命中保持原样并记入 `logs/backfill-miss.jsonl`（不猜、不补）
5. **先 dry-run 打印将要改的 200 条 diff，人工确认后再执行 UPDATE**

### 2.5 事实层 upsert（P2 之后，暂不做）

"每会话恰好 1 条事实记录"需要 `save` 支持按 `session_id + topic` 覆盖，现在是纯 add。
留到 P3，避免 P2 一次性改太多。

## 3. 验收

1. `sync_turn` 写入一条 >800 字的助手结论，库里 `length(content)` 等于原文长度、`right(content,1) <> '…'`
2. 同一轮 `slots` 非空，`statement` 是该结论的第一句
3. P1 的 8 条 query A/B 不退化（`sources` 仍能出现 `fused`/`kw`）
4. 抽提器单测：给定 3 条固定文本，输出与人工标注一致（含负例：`https://` 不能进 `files`）
5. 回填 dry-run 的 94% 命中率在真实执行后复核，未命中条数写入日志

## 4. 开关与回滚

- `BOSHI_WRITE_SLOTS=0` → `sync_turn` 回到 `[:800] + "…"` 的旧行为（进程级 env，与 P1 的 `BOSHI_SEARCH_FUSION` 同风格）
- `slots` 列为 NULL 时所有读路径按旧逻辑处理；回滚不需要改数据
- 回填单独脚本 `~/.boshi/boshi_backfill.py --dry-run|--apply`，不挂进插件

## 5. 风险

- 抽提器误判（如把 `47.6 MB` 当版本号）→ 已用负向断言压制；`slots` 只作检索增强，不作事实来源
- 全文入 content 会让 `_search_sessions`/摘要类读取返回更长文本 → 需检查所有 `content[:N]` 调用点
- 回填依赖 `state.db` 前缀匹配，94% 是抽样值，不是全量承诺
