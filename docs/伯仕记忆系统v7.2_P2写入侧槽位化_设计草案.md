# P2 设计草案 — 写入侧槽位化抽提（原文不截断）

> 状态：**已实施（2026-10-19 夜·三）**；实施记录与实测数据见 §6。原计划分两项：
> ① 助手结论原文全存 + 槽位（已上线）② 用户消息原文全存 + 槽位（§6 已补）
> 前置：P1 读路径（关键词通道 + 融合）已上线并验证（见 `伯仕记忆系统v7.1_检索融合技术文档.md`）

## 1. 为什么必须做（实测基数）

| 项 | 数字 | 来源 |
|---|---|---|
| `assistant_conclusion` 总数 | 1840 | `select count(*) from boshi.memories where topic='assistant_conclusion'` |
| 被 `…` 截断 | 1124（61%） | `right(content,1)='…'` |
| 平均长度 / 最长 | 691 / 4075 | 最长那条丢了 3275 字 |
| `conversation` 截断 | 270 / 3299（8%） | ≤500 字截断 |
| `boshi.memories` 体积 | 84 MB（含 1024 维向量） | `pg_total_relation_size` |

截断不只是"少存字"，它制造**假匹配**：`[2026-07-02] DeepSeek-R1…--tensor-s` 这种半截 token
会被 BM25 的 substring 规则命中，是 `tensor-split 显存` 榜首一度跑偏的直接原因之一。
搜索质量的天花板在写入侧。

**原文可回填**：Hermes `state.db` 里 `messages` 表仍有 34,718 条 assistant 消息
（其中 >800 字 2033 条，最长 28,892 字，合计 593 万字符）；用 boshi 截断行前 60 字做前缀精确匹配，
**200 条抽样命中 187 条（94%）**。→ 历史截断可回填。

## 2. 方案（推荐路线）

### 2.1 抽提器：零模型规则抽提

理由：可复现、零 token、不可能幻觉，与你"不用模型生成内容"的一贯原则一致。
原型 `p2_dryrun2.py` 在 1840 条真实数据上的覆盖率：

```
statement             1834  99.7%
versions               975  53.0%
numbers                777  42.2%
files                  464  25.2%
boundary_envs          454  24.7%
reusable_experience    395  21.5%
decisions              326  17.7%
open_questions         274  14.9%
flags                  260  14.1%
ports                   67   3.6%
commands                21   1.1%
零槽位 230 条（12%）；≥5 个槽位 90 条（5%）
```

规则（全部正则/行级，无模型）：

- `files`：盘符路径 `(?<![A-Za-z0-9_.])[A-Za-z]:[\\/]…`（负向断言挡掉 `https://` 里的 `s:/`）、
  POSIX 绝对路径、相对路径 `a/b/c.py`
- `commands`：行首 `python|pip|uv|git|curl|wget|netstat|schtasks|nvidia-smi|llama-server|ollama|psql|docker|node|npm`
- `flags`：`--flag`；`numbers`：`\d+(\.\d+)?\s?(GB|MB|ms|tok/s|s|°C|%)`；`ports`：`ip:port`
- `versions`：排除 IP 片段与带单位的数字（`47.6 MB` 的 47.6 不算版本）
- 句子级四类：`decisions`（决定/改为/选用/结论是…）、`open_questions`（待/未合并/还没…）、
  `reusable_experience`（铁律/教训/坑/注意/必须…）、`boundary_envs`（端口/显存/CUDA/Python…）
- markdown 表格行先剔除（否则 `| 项目 | 版本 |` 会污染 `boundary_envs`）

已知局限：`commands` 覆盖率 1.1%（大多数命令在正文行内而非行首）、`decisions` 会抓到
"建议换成还能用的：" 这种半句。**不追求召回率**，宁可少抓不可抓错。

### 2.2 存储：原文全存 + 槽位列

```sql
ALTER TABLE boshi.memories ADD COLUMN slots jsonb;       -- 抽提结果
ALTER TABLE boshi.memories  ADD COLUMN raw_len int;      -- 原文长度（对比 content 长度可判断是否完整）
```

- `content` 存**全文**，不再 `[:800] + "…"`（`plugins/boshi/__init__.py:645-646`）
- 增量成本：84MB 表里 content 只占小部分，2033 条 >800 字原文合计约 400 万字符 ≈ 8MB（UTF-8 中文 3 字节）
- `slots` 为空表示未抽提（历史行、或抽提失败），检索行为与今天一致 → 向后兼容

### 2.3 检索侧配合

- 槽位记录带 `slots` 时，`statement` 与 `slots` 的文本一起进关键词索引（P1 的进程内 BM25）
- 原文（长文本）不参与 BM25 全文扫描，避免半截 token 假匹配；只在命中后作为展开层返回
- 排序：槽位命中的记录 > 原文里偶然命中的记录

### 2.4 回填历史（可选，需单独批准）

1. 取 `right(content,1)='…'` 的 1124 条
2. 用前 60 字在 `state.db` `messages`（role='assistant'）精确前缀匹配
3. 命中则覆盖 `content` 为原文、写 `raw_len`、跑抽提写 `slots`
4. 未命中保持原样并记入 `logs/backfill-miss.jsonl`（不猜、不补）
5. **先 dry-run 打印将要改的 200 条 diff，人工确认后再执行 UPDATE**

### 2.5 事实层 upsert（P3 — **2026-10-20 已实现**）

"每会话恰好 1 条事实记录"需要 `save` 支持按 `session_id + topic` 覆盖，那时是纯 add。
**P3 已落地**：`add_memory(..., upsert=True)`（`pg_bridge.py:460` / `chroma_bridge.py:87`）、`boshi_core.save(..., upsert=False)` 透传、MCP `boshi_save(..., upsert=False)`、插件两处 `task_conclusion` 写入加 `upsert=True`。
语义 = 旧有效行置 `is_latest=false` + 新行 `meta.supersedes=<旧 id>`（不物理覆盖，沿用 v5.8 不可变日志）；`session_id`/`topic` 缺一退化为普通 add。
锁用**会话级** `pg_advisory_lock`（`_conn()` 是 autocommit，事务级锁无效）。
细节与实测见 v7.1 技术文档 §11.15。**仍未闭环的部分**：写入时机（见 §7.4）。

## 3. 验收

1. `sync_turn` 写入一条 >800 字的助手结论，库里 `length(content)` 等于原文长度、`right(content,1) <> '…'`
2. 同一轮 `slots` 非空，`statement` 是该结论的第一句
3. P1 的 8 条 query A/B 不退化（`sources` 仍能出现 `fused`/`kw`）
4. 抽提器单测：给定 3 条固定文本，输出与人工标注一致（含负例：`https://` 不能进 `files`）
5. 回填 dry-run 的 94% 命中率在真实执行后复核，未命中条数写入日志

## 4. 开关与回滚

- `BOSHI_WRITE_SLOTS=0` → `sync_turn` 回到 `[:800] + "…"` 的旧行为（进程级 env，与 P1 的 `BOSHI_SEARCH_FUSION` 同风格）
- `slots` 列为 NULL 时所有读路径按旧逻辑处理；回滚不需要改数据
- 回填单独脚本 `~/.boshi/boshi_backfill.py --dry-run|--apply`，不挂进插件

## 5. 风险

- 抽提器误判（如把 `47.6 MB` 当版本号）→ 已用负向断言压制；`slots` 只作检索增强，不作事实来源
- 全文入 content 会让 `_search_sessions`/摘要类读取返回更长文本 → 需检查所有 `content[:N]` 调用点
- 回填依赖 `state.db` 前缀匹配，94% 是抽样值，不是全量承诺

### 6.3 槽位中心化（架构性修正）

原先抽提散在插件里，MCP/其它 agent 走 `boshi_core.save → pg_bridge.add_memory` 时 slots 恒空
（实测近三天 `boshi_api 218 条 / slots 0`，`hermes_plugin 207 条 / slots 91`）。
现改为**唯一写入入口统一补齐**：

```python
# pg_bridge.add_memory，紧随图谱边分流之后
if _slots is None and content and os.environ.get("BOSHI_WRITE_SLOTS", "1") != "0":
    _sm = _slots_mod()
    _sl = _sm.extract(content)
    if _sm.filled_count(_sl):
        _slots = _sl
    if _raw_len is None:
        _raw_len = len(content)
```

契约：调用方传了就用调用方的（插件不重复抽）；异常只跳过、不阻断写入。
自测：1800 字正文 → `length=1800 / raw_len=1800 / source=boshi_api`，slots 含 `ports/numbers/versions/files/statement`。

### 6.4 召回缓存按 query 隔离（`prefetch`）

旧行为：`prefetch()` 只看"距上次写缓存 <300s"，不看 query → 同会话第 2 轮起注入的永远是第 1 轮的召回。
新行为：`_pcache` = `md5(去空白小写query) → (ts, text, count)`，LRU 8 × TTL 300s（`BOSHI_PCACHE_TTL`）；
`queue_prefetch` 与同步兜底都写；旧 `_prefetch_cache` 仅在 query 完全一致时复用。
自测：3 次调用（A / B / A+空格）→ 实际检索 2 次，A≠B、A==C。

### 6.5 同会话扩展：实验证伪（默认关闭）

- 动机：A5 未中 top1 的 14 条中，10 条的 gold 与某个 top5 命中同属一次会话。
- 实现：`_session_expand()`（`pg_bridge.py`），取 top-N 命中的 `session_id` → 同会话内 `assistant_conclusion`、余弦 ≥ 阈值 → 以 `penalty×cos` 并入排序。
- 四组参数全部退化（35 条 gold，auto，baseline **21/30/32**）：

| penalty | min_cos | max_cand | top1 | top3 | top5 |
|---|---|---|---|---|---|
| — | — | — | **21** | **30** | **32** |
| 0.95 | 0.62 | 3 | 16 | 27 | 30 |
| 0.85 | 0.70 | 3 | 18 | 28 | 30 |
| 1.00 | 0.70 | 2 | 15 | 29 | 30 |
| 1.00 | 0.75 | 2 | 17 | 29 | 31 |

结论：扩展候选余弦普遍高于 gold → "同会话结论"并非总是答案，硬并入排序是净负收益。
代码保留、默认 `BOSHI_SESSION_EXPAND=0`，留给日后配合 rerank 再评估。

## 7. 收尾实施记录（2026-10-20 上午）

P2 写路径上线后遗留三件事，本次一次做完；P2+（字段级匹配）同批实现并已开默认，详见 v7.1 §11。

### 7.1 「无槽位就截断」的设计缺口（已修）

旧代码在 `plugins/boshi/__init__.py` 里写的是 `if not slots_meta and len(content) > 500/800: content[:N]+"…"`。这条兜底的**真实触发面比想象的小**：`slots.to_meta()` **总是**返回非空 dict（`{"slots": "...", "raw_len": N}`），所以"抽不出槽位"这一情况根本走不到截断分支；真正会截断的只有 `extract()` **抛异常**（`slots.py` 缺失/损坏）这一条路径。也就是说它是潜在 bug，不是当时担心的"12% 现网损失"。

修法：新增 `_write_slots_enabled()`（读 `BOSHI_WRITE_SLOTS`，默认 `1`），`_slots_meta()` 在其为 `0` 时返回 `{}`；`sync_turn` 的两处截断改成 `if not _write_slots_enabled() and len(...) > N:`——即**只有刻意退回旧行为时才截断**，正常路径（含抽提异常）一律原文全存。

验证 `~/.boshi/scratch/verify_write_truncation.py`（stub `_core` 截获 `save`，不碰真库）：A 正常 1440/2040 字全存、B 抽提抛异常仍全存（旧代码此处会截断）、C `BOSHI_WRITE_SLOTS=0` 得 501/801 字带 `…` —— **6/6 通过**。

### 7.2 user 侧 slots-only 回填（已跑完）

`boshi_backfill.py cmd_slots_only` 加一条：`sm.filled_count(s)==0` 时 **不写库**，保持 `slots IS NULL` = "尚未抽提" 的语义，避免往库里塞 3,288 个空 jsonb。

实测：待抽 5,061 条 → 抽不出 3,288 条（**65.0%**，多为短句/回显/工具输出）→ 写入 **1,773** 条，耗时 86.4s，回滚清单 `~/.boshi/logs/a2-ids-20261020-090849.txt`。写后核验：全库 slots 非空 **2,870**；user 1,953 条中 **227 有槽**（改前 0）；assistant 1,832 条中 **1,710 有槽**（93%）；`raw_len IS NULL` 只剩 17 条；总条数 6,158 不变。
