## 二、问题诊断

### 2.1 现象

用户提出：提起一个新话题（如"微调"），希望伯仕能关联到之前讨论的相关记忆（如"2080Ti推理框架配置"、"vllm部署参数"），但实际搜不到。

### 2.2 根因分析

#### 根因1：查询词 = 当前消息，无联想能力

```python
# 当前实现
def queue_prefetch(self, query, *, session_id=""):
    results = self._core.search(query, ...)  # query 就是用户当前消息
```

用户说"微调"，系统就只搜"微调"，不会想"他可能指2080Ti的微调"。

#### 根因2：知识图谱 search() 只匹配静态列表

`knowledge_graph.py` 第409-418行定义 `KNOWN_ENTITIES`：

```python
KNOWN_ENTITIES = {
    "RTX 2080 Ti", "CUDA", "Turing", "vllm", "llama.cpp",
    "Hermes Agent", "ComfyUI", "MiniMax H3", ...
}
```

"微调"不在列表中 → `graph_source=1` 返回空 → 只有向量搜索。

#### 根因3：向量搜索跨话题相似度不够

- "微调"和"2080Ti推理框架配置"语义距离较大
- 向量搜索只看当前消息的嵌入，不回溯关联话题

### 2.3 验证测试

```bash
# 测试1：图谱搜索"微调" → 空
boshi_core.search("微调", source="graph")  # []

# 测试2：向量搜索"微调" → 有结果但不含推理框架
boshi_core.search("微调", source="vector")  # score 0.744, 但不含2080Ti

# 测试3：图谱query实体"RTX 2080 Ti" → 成功
KnowledgeGraph.query("RTX 2080 Ti")  # 10个关联节点：GPU, CUDA, Turing...
```

**结论**：数据存在，但召回路径不通。需要实体联想机制。

## 三、解决方案

### 3.1 核心思路

**从主查询结果中提取实体名，用这些实体名扩展二次搜索。**

```
主查询："微调"
    ↓
召回记忆：["微调提示词配方", "2080Ti上跑llama.cpp"]
    ↓
提取实体：["2080Ti", "llama.cpp"]
    ↓
扩展查询："2080Ti" → 召回"推理框架配置"、"CUDA依赖"
           "llama.cpp" → 召回"量化参数"、"GGUF格式"
    ↓
合并结果：主查询 + 扩展查询（最多3条）
```

### 3.2 实现细节

**文件**：`plugins/boshi/__init__.py` 第307-354行

```python
def _expand_query_search(self, query: str, existing_lines: List[str]) -> List[str]:
    """从现有召回结果中提取实体名，扩展查询召回关联记忆"""
    try:
        # 1. 提取实体名候选（正则匹配）
        NOISE_MARKERS = ("[transformers]", "PyTorch", "model", " Models")
        entity_candidates = set()
        
        for line in existing_lines:
            # 大写缩写：GPU、API、LLM
            # 数字+字母：2080Ti、v0.20
            # 驼峰命名：OpenAI、ComfyUI
            for match in re.finditer(
                r'(?<![a-zA-Z])([A-Z]{2,})(?![a-zA-Z])'   # 大写缩写
                r'|(?<![a-zA-Z0-9])(\d+[a-zA-Z]+\d+)(?![a-zA-Z0-9])'  # 数字+字母
                r'|([a-zA-Z]+[\u4e00-\u9fff][a-zA-Z0-9]*)',  # 驼峰命名
                line
            ):
                candidate = match.group(0).strip()
                if candidate and len(candidate) >= 2 and candidate not in NOISE_MARKERS:
                    entity_candidates.add(candidate)
        
        # 2. 用提取的实体名扩展查询
        if entity_candidates:
            expanded_queries = list(entity_candidates)[:3]  # 限制数量防超时
            expanded_results = []
            seen = set(...)  # 去重
            
            for entity in expanded_queries:
                ext_result = self._core.search(entity, top_k=2, source="vector")
                for x in ext_result.get("results", []):
                    content = x.get("content", "")
                    if content and content not in seen:
                        expanded_results.append(f"- [{score:.2f}|vector] {content}")
                        seen.add(content[:50])
            
            return expanded_results
    except Exception as e:
        logger.debug("boshi _expand_query_search failed: %s", e)
    return []
```

**调用位置**：第289行，在 `queue_prefetch()` 中

```python
# 改进4：扩展查询——从结果中提取可能的实体名，再搜一次
expanded_lines = self._expand_query_search(query, lines)
if expanded_lines:
    lines.extend(expanded_lines[:3])  # 最多添加3条扩展结果
```

### 3.3 设计权衡

| 决策 | 选择 | 理由 |
|:-----|:-----|:-----|
| 扩展次数 | 最多3次 | 避免超时，平衡召回效果与响应速度 |
| 扩展方式 | 只搜向量库 | 知识图谱search()有静态列表限制，实体名可能也不在列表中 |
| 异常处理 | 吞掉异常 | 扩展失败不影响主流程，只记录debug日志 |
| 结果合并 | 追加不覆盖 | 主查询结果优先级更高，扩展结果作为补充 |

## 四、效果验证

### 4.1 预期效果

**场景1：跨话题联想**
```
用户："微调"
→ 主查询召回：["微调提示词配方", "2080Ti上跑llama.cpp"]
→ 提取实体：["2080Ti", "llama.cpp"]
→ 扩展查询召回：["RTX 2080 Ti 依赖 CUDA", "llama.cpp 量化参数"]
→ 最终注入：5条记忆（当前话题 + 跨话题联想）
```

**场景2：同一话题精确召回**
```
用户："vllm配置"
→ 主查询召回：["vllm启动参数", "vllm显存优化"]
→ 提取实体：["vllm"]
→ 扩展查询召回：可能无新结果（已在主查询中）
→ 最终注入：3-5条相关记忆
```

### 4.2 已知限制

1. **实体提取依赖正则**：无法识别无明确格式的实体（如纯中文名词"注意力机制"）
2. **扩展查询可能引入噪音**：提取的实体名可能不是用户想关联的
3. **不修改记忆数据**：只改召回逻辑，历史数据不变

### 4.3 后续优化方向

- 引入轻量级LLM做实体识别（需权衡延迟）
- 知识图谱动态实体学习（已有 `learn_entities()` 但只用于 save() 时）
- 扩展查询结果排序优化（按实体相关性加权）

## 六、技术要点

### 6.1 与 v6.3 的关系

| 特性 | v6.3（缓存TTL） | v6.4（扩展查询） |
|:-----|:-----|:-----|
| 解决的问题 | prefetch 8秒超时静默跳过 | 跨话题记忆断联 |
| 改动位置 | `prefetch()`/`queue_prefetch()` | `_expand_query_search()` |
| 触发时机 | 每轮对话前 | 每轮对话后台召回时 |
| 副作用 | 无 | 无（纯查询操作） |

### 6.2 与知识图谱的关系

- **互补而非替代**：知识图谱做实体关联，扩展查询做向量召回
- **图谱的局限**：`search()` 只匹配 `KNOWN_ENTITIES` 静态列表
- **扩展查询的优势**：不依赖静态列表，直接从向量库召回语义相关记忆

### 6.3 性能影响

- **额外查询次数**：最多3次（限制扩展查询数）
- **额外延迟**：~2-3秒/次 × 3 = 最多9秒（但走后台线程，不阻塞对话）
- **缓存命中**：5分钟内复用缓存，扩展查询只在无缓存时执行

## 七、总结

v6.4 通过实体联想机制解决了跨话题记忆断联问题，让伯仕像人一样能从当前话题联想到相关历史记忆。这是记忆系统从"精确匹配"向"语义联想"迈出的重要一步。

**下一步**：考虑引入 LLM 做更智能的实体识别和查询扩展，但需权衡延迟成本。
