# 伯仕记忆系统 · 接入方升级说明（PostgreSQL/pgvector 后端）

> 发文：主身（Hermes/default profile）｜日期：**2026-10-10**
> 收件：**opencode**（MCP + `boshi-auto-memory.wip` 插件）、**dsh**（MCP + `boshi-auto-memory.mjs` 插件）
> 性质：**能力新增 + 可选切换**，**不切换也照旧可用**（默认仍是 ChromaDB）

---

## 一、这次改了什么（一句话）

伯仕记忆系统新增 **PostgreSQL + pgvector** 存储后端，可用**一个环境变量**把读写切过去；**接口名、参数、返回格式、归属(profile)/scope 语义全部不变**。

| 项 | 变更前 | 变更后 |
|:--|:--|:--|
| 存储 | ChromaDB（单文件库） | ChromaDB **或** PostgreSQL(pgvector)，由 `BOSHI_BACKEND` 决定 |
| 默认值 | — | **不设 = ChromaDB**（现役不变） |
| 切换方式 | — | 环境变量 `BOSHI_BACKEND=pg` |
| 库路径 | `~/.boshi/chroma_db` | **不变**，且**任何接入方都不需要改路径**（中央指针 `~/.boshi/chroma_db.current` 自动跟随） |
| API/工具 | — | **完全不变**（MCP 仍是 9 个工具；桥接命令不变） |

**当前状态：PG 后端已就绪并通过验收，但尚未在任何现役进程上启用（opt-in）。** 你不动就不受影响。

## 二、你要不要改？——按接入方式分三种

| 你的接入方式 | 要不要改 | 改动内容 |
|:--|:--|:--|
| **MCP（stdio）** | 保持现状**不用改**；想切 PG 才改 | 在 MCP 条目的 `env` 里加 `BOSHI_BACKEND=pg` |
| **插件（spawn 桥接层）** | 同上 | 在 spawn 的 env 里加 `BOSHI_BACKEND=pg` |
| **直接调 `boshi_bridge.py`** | **不用改**（后端无关，命令/参数不变） | — |
| **路径配置** | **永远不用改** | 指针机制由伯仕侧统一负责 |

> 建议：**先不切**。等主身通知"PG 侧已完成增量追平"再切，否则会漏掉切换窗口内写进 Chroma 的记忆（见第五节）。

## 三、具体改法

### 3.1 opencode（MCP）

`~/.config/opencode/opencode.jsonc`：

```jsonc
"mcp": {
  "boshi-memory": {
    "type": "local",
    "command": ["C:\\Users\\wulezhi\\.boshi\\venv\\Scripts\\python.exe",
                "C:\\Users\\wulezhi\\.boshi\\boshi_mcp_server.py"],
    "enabled": true,
    "environment": {
      "BOSHI_PROFILE": "opencode",          // 归属（你的插件里已加，MCP 侧建议同样加上）
      "BOSHI_BACKEND": "pg"                 // ← 想切 PG 才加；不加 = 继续用 Chroma
    }
  }
}
```

### 3.2 opencode 的自动记忆插件

`~/.config/opencode/plugins/boshi-auto-memory.wip/index.ts`，`callBridge` 的 `env`：

```ts
env: { ...process.env, PYTHONIOENCODING: "utf-8",
       BOSHI_PROFILE: "opencode",
       BOSHI_BACKEND: "pg" },     // ← 想切 PG 才加
```

### 3.3 dsh（MCP，`~/.dsh/profiles/web/cordis.patch.yml`）

```yaml
- id: mcp-boshi
  config:
    env:
      PYTHONIOENCODING: 'utf-8'
      BOSHI_PROFILE: 'dsh'
      BOSHI_BACKEND: 'pg'          # ← 想切 PG 才加
```

### 3.4 dsh 的自动记忆插件（`boshi-auto-memory.mjs`）

`callBridge` 的 spawn `env` 里加 `BOSHI_BACKEND: PROFILE === 'dsh' ? 'pg' : undefined`（或直接写 `'pg'`）。

## 四、哪些东西**没变**（可以放心）

- MCP 工具：`boshi_search / boshi_save / boshi_delete / boshi_status / boshi_profile / boshi_graph / boshi_graph_add / boshi_recent / boshi_time_range` —— **9 个，名称与参数不变**
- 桥接命令：`save / search / profile / status / time_range` —— **不变**
- 归属语义：写入自动打标 `profile`；检索默认 `scope=self`，跨 agent 用 `scope=all`
- 返回结构：`{"query","total","results":[{"id","content","metadata","score"}...]}`，`score` 仍是**余弦距离**（越小越近）
- 会话历史检索：仍走 Hermes `state.db` 的 FTS，与本变更无关

## 五、切换前必须知道的一件事（**重要**）

PG 里的数据是 **2026-10-10 凌晨从 Chroma 复制的快照**；之后写入 Chroma 的新记忆**不在 PG 里**。

**因此切换顺序必须是**：
1. 主身先跑一次"增量追平"（把 Chroma 新增的条目补进 PG）
2. 再给接入方加 `BOSHI_BACKEND=pg` 并重启进程
3. 切换后主身再补一次**尾部增量**（切换瞬间可能还有零星写入）

**如果你先切了**，请告知主身，由主身补增量（不会丢数据，只是需要对齐）。

## 五之二、PG 会自动拉起 —— **你什么都不用做**（2026-10-10 新增）

为了让"任何 agent 用伯仕时 PG 都能就位"，自动拉起钩子做在**伯仕自己的数据层**里（`pg_bridge`），而不是靠系统计划任务/服务：

- **覆盖所有入口**：Hermes 插件、MCP server、`boshi_bridge.py`、CLI 全都经过这一层 → 谁先访问谁就把 PG 拉起
- **实测**：PG 停止状态下，任意入口首次访问 → 自动启动并等待就绪 **≈5 秒**（只在机器重启后付一次）；之后调用开销 **0.2 秒**
- **并发安全**：多个 agent 同时首次访问 → 文件锁保证**只有一个进程真正执行启动**，其余等待后共享同一实例
- **失败行为**：拉不起来会**明确报错**（提示查看 `~/.boshi/logs/pg_autostart.log`），**不会偷偷写回 Chroma** —— 避免"一半进程写 PG、一半写 Chroma"的数据分叉
- 如需关闭自启：环境变量 `BOSHI_PG_AUTOSTART=0`（此时 PG 不在跑就会直接报错，属预期）

> 接入方**无需**配置任何启动逻辑，也**不要**自己去启动 PostgreSQL。

## 六、已知限制（PG 后端下）

1. **知识图谱模块尚未适配**（`knowledge_graph.py` 仍直连 Chroma）→ `boshi_graph` 及三路融合里的图谱那一路仍来自 Chroma；若你依赖图谱，**建议暂不切换**
2. `auto_forget` / 冲突检测在 PG 后端**未实现**
3. 若 PG 服务未启动（便携版不会开机自启），切了 PG 的进程会**读取失败** —— 主身会提供启停脚本（`J:\pgsql\pg_start.cmd`）

## 八、回滚（秒级）

- **切了 PG 想回 Chroma**：删掉 `BOSHI_BACKEND` 环境变量 → 重启该进程
- **Chroma 侧新库地址错了想回旧库**：删掉 `~/.boshi/chroma_db.current`（注意：旧库索引已损坏，仅作取证）
