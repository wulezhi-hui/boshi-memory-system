## 二、为什么升级（动机，含事故驱动）

1. **并发写压力**：伯仕库被 **8 个进程**同时持有（4 个 profile 的 Hermes 插件 + 常驻 MCP server + dsh/opencode/desktop）；ChromaDB 是嵌入式文件库，多写者场景最弱
2. **事故**：2026-10-09 15:43 HNSW 索引损坏（`Error loading hnsw index`），检索整体失效，opencode 报"记忆调用失败"；恢复需**重新编码重建 5 万条**（约 1.5 小时）
3. **增长与备份**：单文件 + 段文件的备份/迁移手段粗糙；PG 有 `pg_dump`、事务、并发、真 SQL
4. **集中化愿景**：把伯仕记忆 / 佛学向量库 / zhishiku 收敛到一个 PG 实例（各自 schema）

### 3.1 后端调度（chroma_bridge.py 末尾）

```python
BACKEND = os.environ.get("BOSHI_BACKEND", "chroma").strip().lower()
if BACKEND == "pg":
    import pg_bridge as _pgb
    for _n in _PUBLIC_API:            # 15 个公开 API
        globals()[_n] = getattr(_pgb, _n)
```
- 只替换**公开 API**；`_get_collection/_get_client` 等内部辅助仍指 Chroma（诊断用）
- **加载失败自动退回 Chroma**（不允许"记忆整体不可用"）

### 3.2 库目录指针（v6.6 之后的加固）

解析优先级：`BOSHI_CHROMA_DIR` 环境变量 > **`~/.boshi/chroma_db.current`（指针文件，一行路径）** > 默认 `~/.boshi/chroma_db`。
→ 「换库」= 改指针文件（秒级、可回滚），取代原手册的「停全部持有者 → 改目录名」（该步骤在本机从未跑通，受文件句柄阻塞）。

### 3.4 PG 自动拉起（钩子，2026-10-10）

**为什么不用计划任务/服务**：服务（`pg_ctl register`）需管理员且服务账户访问 `J:\pgdata` 有权限坑，破坏"免安装便携"初衷；计划任务只在登录后生效。**钩子做在数据层** → 覆盖全部入口（Hermes 插件 / MCP server / 桥接 / CLI），零系统配置。

**实现（`pg_bridge.ensure_pg_running()`）**：

```
_conn() 连接失败 → ensure_pg_running(assume_down=True)
    ├─ 端口/握手探测（已在跑则直接返回）
    ├─ 抢占文件锁 ~/.boshi/pg_autostart.lock（陈锁 >60s 可接管）
    ├─ 拿锁后二次确认 → 真正 start（脱离调用方进程树：DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW）
    ├─ 轮询 SELECT 1（0.25s 间隔，上限 BOSHI_PG_START_TIMEOUT=30s）
    └─ 未拿到锁的进程：等待其它进程拉起，再复用同一实例
失败 → 抛 RuntimeError（含日志路径与排查步骤）——**绝不静默退回 Chroma**（避免 PG/Chroma 数据分叉）
```

可用环境变量：`BOSHI_PG_BIN`（默认 `J:/pgsql/bin`）、`BOSHI_PG_DATA`（`J:/pgdata`）、`BOSHI_PG_AUTOSTART`（`0`=关闭）、`BOSHI_PG_START_TIMEOUT`（默认 **90 秒** —— 覆盖"异常关机后崩溃恢复需 ~35 秒"的情况；正常冷启动仅 ~1–5 秒）。

**⚠️ 启动方式铁律（2026-10-10，经过一整轮试错才定稿）**：

```python
# ✅ 当前采用：隐藏控制台（无可见窗口）
CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW
# 备选：DETACHED_PROCESS —— 会看到 cmd 黑窗口（见下）
```

Windows 上的两条硬事实（实测，别再试错）：

1. **不能直接启动 `postgres.exe`**：若调用方是管理员令牌，PG 会拒绝并报
   "不能以管理员权限的用户运行 PostgreSQL 服务器"。`pg_ctl` 会用**受限令牌**
   启动 postmaster —— 这就是 Windows 上必须经 pg_ctl 的原因。
2. **`pg_ctl` 固定经 `cmd.exe /C "postgres ... < nul >> LOG 2>&1"` 启动**
   （源码如此，无法绕过）。pg_ctl 若自己没有可继承的控制台（`DETACHED_PROCESS`），
   cmd 会**新分配一个可见控制台窗口**（用户会看到黑窗口），postmaster 挂在其上。

→ 所以只能**二选一**：`DETACHED_PROCESS`（可见窗口）或 `CREATE_NO_WINDOW`（隐藏控制台）。
两种方式 postmaster 都挂在 cmd 的控制台上，控制台事件（Ctrl+C / 关闭）都能整库打死
（2026-10-10 两次 `0xC000013A` —— 真凶是用户把那个黑窗口关掉了）。

→ **已根治（2026-10-10 02:40）：注册 Windows 服务 `boshi-pg`**，账号 `NT AUTHORITY\NetworkService`。
服务**没有控制台** → 机制上免疫控制台事件；且**开机自启 + SCM 失败自动重启（5s/10s/30s）**。
钩子改为**服务优先**：

```python
st = _service_state()                 # sc query boshi-pg
if st in ("RUNNING", "START_PENDING", "STOP_PENDING"):
    return                            # 交给服务自愈，绝不另起实例
if st != "absent":
    sc.exe start boshi-pg             # 服务停着 → 拉起服务
# 服务不可用/无权限 → 回退下面的 pg_ctl 独立启动（兜底，保证"绝不起不来"）
```

配套加固：pg_ctl 报错落 `~/.boshi/logs/pg_ctl_start.log`（不再丢 DEVNULL）；
`pg.log` 被占用时自动改用带时间戳的日志名（孤儿锁死不再导致"永远起不来"）；
启动超时自动执行"pg.log 是否可写"体检；`_conn()` 加 `SELECT 1` 探活 + 失效自动重建。

**实测（2026-10-10）**：

| 场景 | 结果 |
|:--|:--|
| 冷启动（PG 停止 → 任意入口访问） | 自动拉起，**≈5.0 s 就绪**，检索正常 ✅ |
| 并发（3 进程同时要求拉起） | 日志精确统计：**仅 1 次真正发起启动**，其余等待后共享实例 ✅ |
| 已有 PG 时的额外开销 | **0.2 s**（含 python 启动与 psycopg 导入）✅ |
| 关闭自启 / 拉不起来 | 响亮报错（RuntimeError + 排查提示）✅ |
| 进程树 | 脱离调用方；agent 进程被杀不会连带杀死 PG ✅ |

### 3.5 按 profile 切换后端（`backends.json`，2026-10-10）

为了让"**按接入方精细切换**"成为可能（不能全局设环境变量，否则会把所有 agent 一起切），新增中央配置文件：

```
~/.boshi/backends.json
{
  "default": "pg",      // Hermes 主身
  "*": "chroma"         // 其余接入方（显式写，避免误切）
}
```

**解析优先级**（`chroma_bridge._resolve_backend()`，import 时执行一次）：
```
BOSHI_BACKEND 环境变量  >  backends.json[当前 profile]  >  backends.json["*"]  >  默认 "chroma"
```
其中"当前 profile"由 `resolve_profile()` 推导（`BOSHI_PROFILE` > `HERMES_HOME` 推导 > default）
→ **谁在用伯仕，就按谁在配置里的取值**；接入方零改动、无需各自配置。

**实测解析矩阵**：default→`pg`(backends.json[default]) / opencode→`chroma`(通配) / dsh→`chroma`(通配) / 显式 env→`pg`(env 优先) ✅

**⚠️ 两个要点**：
1. **后端在 import 时解析** → 改 `backends.json` 或 env 后**必须重启该进程**才生效
2. **增量同步是单向的（Chroma → PG）**：某个 profile 切到 PG 后，它新写的记忆**只进 PG**；若将来把该 profile 回滚到 Chroma，这段 PG 期记忆不在 Chroma 里（需反向同步或接受缺口）

## 四、数据模型

```sql
-- 记忆条目（非图谱）
CREATE TABLE boshi.memories (
  id              uuid PRIMARY KEY,          -- 沿用 Chroma 的 memory_id
  content         text NOT NULL,
  embedding       vector(1024),              -- bge-m3，cosine
  profile         text,                      -- 归属：default/dsh/opencode/desktop/zuojia
  source          text,                      -- hermes_plugin / boshi_api / ...
  topic           text, role text, session_id text,
  meta            jsonb,                     -- 其余元数据（形状不定，jsonb 兜底）
  is_latest       boolean NOT NULL DEFAULT true,
  created_at      timestamptz,               -- 由 timestamp 换算
  version_created double precision);

-- 图谱边（原 type=relation）
CREATE TABLE boshi.graph_edges (
  id uuid PRIMARY KEY, entity_a text, entity_b text, relation text,
  content text, embedding vector(1024), version_created double precision);
```

**索引（12 个）**：两表各 HNSW(cosine)；`memories(profile) WHERE is_latest`、`source`、`created_at DESC`、`topic`、`meta GIN`；`graph_edges(entity_a)`、`(entity_b)`、`(entity_a,entity_b,relation)`。

**关键结构性收益**：Chroma 时代"图谱边占 91% 且必须用 `type != relation` 补丁过滤"的问题，在 PG 里变成**天然的表隔离**（边在另一张表），相关 where 补丁退休。

## 五、迁移方法（4 步，可复用）

| 步 | 做法 | 实测 |
|:--|:--|:--|
| 1 建表 | 执行 `pg_boshi_schema.sql`（2 表 12 索引） | 秒级 |
| 2 **全量复制** | `col.get(include=['embeddings'])` **直接读向量**（免重算）→ CSV → `psql \copy` | 导出 **43 s**（51,097 条 / 577 MB CSV）、导入 **163 s** |
| 3 **对拍** | 同批 query 比两后端 top10 | 重合 **0.985**、top1 一致 19/20 |
| 4 **改指向** | 给进程加 `BOSHI_BACKEND=pg` 并重启；**切换前补增量** | opt-in，未执行 |

**为什么不重算向量**：Chroma 健康时可用 API 直接读出 1024 维向量；只有在 HNSW 索引**损坏**时才需要解析段文件——而那次实测证明**行序↔id 映射不可恢复**（尾部 8 字节既非 label 也非 seq_id），故损坏场景只能重算。

7. ✅ **重启后"二次死亡"已修（2026-10-10 事故）**：启动标志带 `CREATE_NO_WINDOW` → 隐藏控制台 → 控制台关闭/Ctrl+C → 整库 `0xC000013A` 被打死，并留下**孤儿子进程锁死 `pg.log`**（后续启动全部 `Permission denied`）。已补上 pg_ctl 报错留痕 + 启动失败自动体检；启动标志几经试错，**最终由第 9 条的服务方案根治**（详见工作日志 2026-10-10 条目）

9. ✅ **PG 的"窗口/控制台"问题已根治（2026-10-10，注册成 Windows 服务）**：Windows 上 PG 必须经 pg_ctl（受限令牌），而 pg_ctl 必经 cmd.exe → 之前只能二选一（隐藏控制台=无窗口 / DETACHED=可见窗口），两者 postmaster 都挂在 cmd 控制台上、控制台事件能打死整库（用户关掉那个黑窗口 = 两次 `0xC000013A` 的真凶）。**现改为注册 Windows 服务 `boshi-pg`**：账号 `NT AUTHORITY\NetworkService`（非管理员令牌 → PG 接受），服务**无控制台** → 免疫控制台事件，且**开机自启 + SCM 失败自动重启（5s/10s/30s）**。钩子已改为**服务优先**（服务在跑就不另起实例；停着就 `sc start`；服务不可用才回退 pg_ctl）。运维/回滚见工作日志 2026-10-10 条目与 §九
10. ✅ **读回时间戳已补（2026-10-10，由 dsh 侧反馈驱动）**：`_META_SEL` 原来只拼 `profile`/`isLatest`，**不还原 `timestamp`** → 凡 `meta` 里没写 timestamp 的记录（实测 **4,589 条**，几乎全库）在调用方按 `metadata.timestamp` 排序/展示时"没有时间"。已改为 `COALESCE(EXTRACT(EPOCH FROM created_at), NULLIF(meta->>'timestamp','')::float8)`（**列权威、meta 兜底**）。同时 `backends.json` 显式加 `dsh/opencode = pg` —— 否则漏带 `BOSHI_BACKEND` 的调用路径会静默落到 Chroma（读=0 条、写=数据分叉）

## 九、运维

```bash
# 启停（正常情况下什么都不用做：服务开机自启；钩子会在需要时拉起它）
net start boshi-pg         # 启动服务（推荐方式；无窗口、无控制台）
net stop  boshi-pg         # 停止服务
sc query  boshi-pg         # 查看状态（RUNNING / STOPPED）
sc failure boshi-pg reset= 86400 actions= restart/5000/restart/10000/restart/30000   # 失败自动重启（已配置）
J:\pgsql\bin\pg_ctl.exe unregister -N boshi-pg   # 卸载服务（回滚到钩子独立启动）
J:\pgsql\pg_start.cmd      # 备用：走钩子启动（已改为无窗口方式）
# ❌ 绝不要手工敲 pg_ctl.exe 启动：postmaster 会依附你那个 cmd 窗口，
#    窗口一关整库就被控制台事件打死（0xC000013A，2026-10-10 实测事故）

# 备份（一条命令）
J:/pgsql/bin/pg_dump.exe -h 127.0.0.1 -U postgres -d hermes_data -Fc -f J:/backup/hermes_data_YYYYMMDD.dump

# 体量速查
psql -c "SELECT pg_size_pretty(pg_total_relation_size('boshi.memories')),
                pg_size_pretty(pg_total_relation_size('boshi.graph_edges'))"
# 现状：memories 63 MB / graph_edges 611 MB（边的向量索引偏浪费，见下）
```

**优化建议（择机执行）**：图谱边默认不参与召回 → `graph_edges` 的 HNSW 索引可去掉（省 ~500 MB，写入更快）。

## 十、本次踩坑清单（可复用）

| 坑 | 现象 | 处理 |
|:--|:--|:--|
| 在会被超时清理的命令里起 PG | `pg_ctl start` 前台跑 + 工具超时 → 子进程被连带杀死 → `0xC0000142` → PG 崩溃恢复 | 用 `Start-Process -WindowStyle Hidden` 脱离调用方进程树 |
| 中文经 `psql -c` 传参 | `invalid byte sequence for encoding "UTF8": 0xba` | 含中文的 SQL 一律写 UTF-8 文件用 `psql -f` |
| **MCP 并发调用 + 惰性单例无锁** | `boshi_search` 偶发 `cannot import name 'AutoTokenizer' from 'transformers'`（**save 却成功**）——单线程永不复现 | 给 `onnx_embed._get_cached_ef()` 加**双检锁**；并发首次导入第三方库一律要加锁 |
| `get_collection()` 未传 EF | 查询报 `expecting 1024, got 384`（Chroma 用默认 MiniLM） | **必须显式传 `embedding_function`** |
| `col.get(limit=N)` 取内部顺序 | 取样全是 1 字记忆/短边（重建按长度升序） | 取样必须带 `where` 过滤 |
| 系统代理开着但代理程序没跑 | pip/uv 全失败（`WinError 10061`） | `pip install --proxy "" -i <国内镜像>`；**不动注册表 ProxyEnable** |
| PG 原生中文全文检索 | `show_trgm('显存优化')` = `{}`；`to_tsvector('simple',中文)` 整串一个 token | 路线：Python 侧切词（1/2-gram）→ `tsvector` + GIN，或向量检索为主 |
| **想在 Windows 上"无窗口又无控制台"启动 PG** | 直接 spawn `postgres.exe` → PG 拒绝（"不能以管理员权限的用户运行"）；改用 `DETACHED_PROCESS` 摆脱控制台 → pg_ctl 只能在无控制台时经 `cmd.exe` 启动，cmd 于是**新分配一个可见黑窗口** | 二选一：`CREATE_NO_WINDOW`（隐藏控制台，无窗口）或 `DETACHED_PROCESS`（可见窗口）；**根治=注册 Windows 服务**（需管理员，属架构变更） |
| **不清楚 pg_ctl 到底怎么启动 postmaster** | 排查时发现 `cmd.exe /C "postgres ... < nul >> log"` 这层包装，且 postmaster 的父进程是 cmd | Windows 上 PG 必须经 pg_ctl（受限令牌）；pg_ctl 必经 cmd.exe：**控制台与窗口问题都源于这两层** |
| **postmaster 死后留下孤儿子进程** | 孤儿继承 `pg.log` 写句柄 → `pg_ctl start` 报 `could not open log file: Permission denied` → 之后每次启动**静默失败**（pg.log 一行不写） | 先 `taskkill /F /PID <孤儿>` 再启动；启动失败时做"pg.log 是否可写"体检（已内置） |
| **把 pg_ctl 报错丢 DEVNULL** | 自动拉起日志只有"拉起失败或超时（90 秒）"，真因完全不可见 | pg_ctl 的 stdout/stderr 落 `logs/pg_ctl_start.log`（已内置） |
| **时间戳形态不统一（ISO 字符串 vs float）** | ISO 字符串喂给 `float()` → 抛异常被吞 → `created_at=NULL` → 该条对 `time_range`/`recent` 等时间线查询**永久隐形**（向量/关键词召回仍正常，所以很难察觉） | 每个后端都要**归一化时间戳**（`pg_bridge._norm_ts()`；Chroma 侧是 `_normalize_metadata`）；跨后端迁移时先比对两侧归一化逻辑 |
| **按 profile 的通配键（静默错库）** | 已切后端的接入方没在 `backends.json` 显式列名 → 漏带 `BOSHI_BACKEND` 的调用路径静默落到另一个库（读=0 条还好发现，**写=数据分叉最危险**） | 切接入方要**两头一起改**：`backends.json` 显式列名 + 接入方 env；排查先**分层复现**（数据层→中转层→调用方），别猜根因 |
| **读回 metadata 不还原列字段** | PG 把时间存成 `created_at` 列，读回却只拼 `meta` → 调用方看到 `metadata.timestamp` 为空 → 时间线排序/展示全失效（实测 4,589 条受影响，且**不报错**） | 读回时要把列**还原成调用方契约里的字段**（`_META_SEL` 已补 `COALESCE(EXTRACT(EPOCH FROM created_at), NULLIF(meta->>'timestamp','')::float8)`）；迁移后端时逐一核对"读回字段集"是否与旧后端同形 |

## 十一、回滚

| 场景 | 操作 |
|:--|:--|
| 切了 PG 想回 Chroma | 删除 `BOSHI_BACKEND` 环境变量 → 重启进程 |
| 想回旧 Chroma 库 | 删除 `~/.boshi/chroma_db.current`（注意旧库索引已损坏，仅供取证） |
| PG 服务不可用 | 同上；`pg_bridge` 加载/连接失败时 `chroma_bridge` 会自动退回 Chroma |
