## 二、为什么升级（动机，含事故驱动）

1. **并发写压力**：伯仕库被 **8 个进程**同时持有（4 个 profile 的 Hermes 插件 + 常驻 MCP server + dsh/opencode/desktop）；ChromaDB 是嵌入式文件库，多写者场景最弱
2. **事故**：2026-10-09 15:43 HNSW 索引损坏（`Error loading hnsw index`），检索整体失效，opencode 报"记忆调用失败"；恢复需**重新编码重建 5 万条**（约 1.5 小时）
3. **增长与备份**：单文件 + 段文件的备份/迁移手段粗糙；PG 有 `pg_dump`、事务、并发、真 SQL
4. **集中化愿景**：把伯仕记忆 / 佛学向量库 / zhishiku 收敛到一个 PG 实例（各自 schema）

## 三、架构

```
                 ┌──────────────────────────────────────────┐
   MCP server ──┤                                          │
   bridge      ──┤  boshi_core / knowledge_graph / CLI      │
   Hermes 插件  ─┤            ↓                              │
                 │      chroma_bridge  （调度 + 公共 API）   │
                 │       ├─ BOSHI_BACKEND 未设 → ChromaDB   │
                 │       └─ BOSHI_BACKEND=pg  → pg_bridge   │
                 └──────────────────────────────────────────┘
                                 ↓                    ↓
                        ~/.boshi/chroma_db*     PostgreSQL 17.6 + pgvector 0.8.2
                        （指针可切换）            J:\pgdata（数据不占 C 盘）
```

### 3.1 后端调度（chroma_bridge.py 末尾）

```python
BACKEND = os.environ.get("BOSHI_BACKEND", "chroma").strip().lower()
if BACKEND == "pg":
    import pg_bridge as _pgb
    for _n in _PUBLIC_API:            # 15 个公开 API
        globals()[_n] = getattr(_pgb, _n)
```
- 只替换**公开 API**；`_get_collection/_get_client` 等内部辅助仍指 Chroma（诊断用）
- **加载失败自动退回 Chroma**（不允许"记忆整体不可用"）

### 3.2 库目录指针（v6.6 之后的加固）

解析优先级：`BOSHI_CHROMA_DIR` 环境变量 > **`~/.boshi/chroma_db.current`（指针文件，一行路径）** > 默认 `~/.boshi/chroma_db`。
→ 「换库」= 改指针文件（秒级、可回滚），取代原手册的「停全部持有者 → 改目录名」（该步骤在本机从未跑通，受文件句柄阻塞）。

### 3.3 PG 实例

| 项 | 值 |
|:--|:--|
| 版本 | PostgreSQL **17.6** + pgvector **0.8.2**（便携版，无服务/无注册表） |
| 程序 / 数据 | `J:\pgsql` / `J:\pgdata` |
| 监听 | `127.0.0.1:5432`，用户 `postgres`（trust） |
| 连接串 | `postgresql://postgres@127.0.0.1:5432/hermes_data`（可用 `BOSHI_PG_DSN` 覆盖） |
| 启停 | `J:\pgsql\pg_start.cmd` / `pg_stop.cmd`（便携版不注册服务；**平时无需手动启停** —— 由数据层钩子按需自动拉起，见 §3.4） |
| 调优 | shared_buffers 1GB、maintenance_work_mem 512MB、work_mem 32MB、random_page_cost 1.1 |

### 3.4 PG 自动拉起（钩子，2026-10-10）

**为什么不用计划任务/服务**：服务（`pg_ctl register`）需管理员且服务账户访问 `J:\pgdata` 有权限坑，破坏"免安装便携"初衷；计划任务只在登录后生效。**钩子做在数据层** → 覆盖全部入口（Hermes 插件 / MCP server / 桥接 / CLI），零系统配置。

**实现（`pg_bridge.ensure_pg_running()`）**：

```
_conn() 连接失败 → ensure_pg_running(assume_down=True)
    ├─ 端口/握手探测（已在跑则直接返回）
    ├─ 抢占文件锁 ~/.boshi/pg_autostart.lock（陈锁 >60s 可接管）
    ├─ 拿锁后二次确认 → 真正 start（脱离调用方进程树：DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW）
    ├─ 轮询 SELECT 1（0.25s 间隔，上限 BOSHI_PG_START_TIMEOUT=30s）
    └─ 未拿到锁的进程：等待其它进程拉起，再复用同一实例
失败 → 抛 RuntimeError（含日志路径与排查步骤）——**绝不静默退回 Chroma**（避免 PG/Chroma 数据分叉）
```

可用环境变量：`BOSHI_PG_BIN`（默认 `J:/pgsql/bin`）、`BOSHI_PG_DATA`（`J:/pgdata`）、`BOSHI_PG_AUTOSTART`（`0`=关闭）、`BOSHI_PG_START_TIMEOUT`（默认 **90 秒** —— 覆盖"异常关机后崩溃恢复需 ~35 秒"的情况；正常冷启动仅 ~1–5 秒）。

**实测（2026-10-10）**：

| 场景 | 结果 |
|:--|:--|
| 冷启动（PG 停止 → 任意入口访问） | 自动拉起，**≈5.0 s 就绪**，检索正常 ✅ |
| 并发（3 进程同时要求拉起） | 日志精确统计：**仅 1 次真正发起启动**，其余等待后共享实例 ✅ |
| 已有 PG 时的额外开销 | **0.2 s**（含 python 启动与 psycopg 导入）✅ |
| 关闭自启 / 拉不起来 | 响亮报错（RuntimeError + 排查提示）✅ |
| 进程树 | 脱离调用方；agent 进程被杀不会连带杀死 PG ✅ |

### 3.5 按 profile 切换后端（`backends.json`，2026-10-10）

为了让"**按接入方精细切换**"成为可能（不能全局设环境变量，否则会把所有 agent 一起切），新增中央配置文件：

```
~/.boshi/backends.json
{
  "default": "pg",      // Hermes 主身
  "*": "chroma"         // 其余接入方（显式写，避免误切）
}
```

**解析优先级**（`chroma_bridge._resolve_backend()`，import 时执行一次）：
```
BOSHI_BACKEND 环境变量  >  backends.json[当前 profile]  >  backends.json["*"]  >  默认 "chroma"
```
其中"当前 profile"由 `resolve_profile()` 推导（`BOSHI_PROFILE` > `HERMES_HOME` 推导 > default）
→ **谁在用伯仕，就按谁在配置里的取值**；接入方零改动、无需各自配置。

**实测解析矩阵**：default→`pg`(backends.json[default]) / opencode→`chroma`(通配) / dsh→`chroma`(通配) / 显式 env→`pg`(env 优先) ✅

**⚠️ 两个要点**：
1. **后端在 import 时解析** → 改 `backends.json` 或 env 后**必须重启该进程**才生效
2. **增量同步是单向的（Chroma → PG）**：某个 profile 切到 PG 后，它新写的记忆**只进 PG**；若将来把该 profile 回滚到 Chroma，这段 PG 期记忆不在 Chroma 里（需反向同步或接受缺口）

## 四、数据模型

```sql
-- 记忆条目（非图谱）
CREATE TABLE boshi.memories (
  id              uuid PRIMARY KEY,          -- 沿用 Chroma 的 memory_id
  content         text NOT NULL,
  embedding       vector(1024),              -- bge-m3，cosine
  profile         text,                      -- 归属：default/dsh/opencode/desktop/zuojia
  source          text,                      -- hermes_plugin / boshi_api / ...
  topic           text, role text, session_id text,
  meta            jsonb,                     -- 其余元数据（形状不定，jsonb 兜底）
  is_latest       boolean NOT NULL DEFAULT true,
  created_at      timestamptz,               -- 由 timestamp 换算
  version_created double precision);

-- 图谱边（原 type=relation）
CREATE TABLE boshi.graph_edges (
  id uuid PRIMARY KEY, entity_a text, entity_b text, relation text,
  content text, embedding vector(1024), version_created double precision);
```

**索引（12 个）**：两表各 HNSW(cosine)；`memories(profile) WHERE is_latest`、`source`、`created_at DESC`、`topic`、`meta GIN`；`graph_edges(entity_a)`、`(entity_b)`、`(entity_a,entity_b,relation)`。

**关键结构性收益**：Chroma 时代"图谱边占 91% 且必须用 `type != relation` 补丁过滤"的问题，在 PG 里变成**天然的表隔离**（边在另一张表），相关 where 补丁退休。

## 五、迁移方法（4 步，可复用）

| 步 | 做法 | 实测 |
|:--|:--|:--|
| 1 建表 | 执行 `pg_boshi_schema.sql`（2 表 12 索引） | 秒级 |
| 2 **全量复制** | `col.get(include=['embeddings'])` **直接读向量**（免重算）→ CSV → `psql \copy` | 导出 **43 s**（51,097 条 / 577 MB CSV）、导入 **163 s** |
| 3 **对拍** | 同批 query 比两后端 top10 | 重合 **0.985**、top1 一致 19/20 |
| 4 **改指向** | 给进程加 `BOSHI_BACKEND=pg` 并重启；**切换前补增量** | opt-in，未执行 |

**为什么不重算向量**：Chroma 健康时可用 API 直接读出 1024 维向量；只有在 HNSW 索引**损坏**时才需要解析段文件——而那次实测证明**行序↔id 映射不可恢复**（尾部 8 字节既非 label 也非 seq_id），故损坏场景只能重算。

## 十、本次踩坑清单（可复用）

| 坑 | 现象 | 处理 |
|:--|:--|:--|
| 在会被超时清理的命令里起 PG | `pg_ctl start` 前台跑 + 工具超时 → 子进程被连带杀死 → `0xC0000142` → PG 崩溃恢复 | 用 `Start-Process -WindowStyle Hidden` 脱离调用方进程树 |
| 中文经 `psql -c` 传参 | `invalid byte sequence for encoding "UTF8": 0xba` | 含中文的 SQL 一律写 UTF-8 文件用 `psql -f` |
| **MCP 并发调用 + 惰性单例无锁** | `boshi_search` 偶发 `cannot import name 'AutoTokenizer' from 'transformers'`（**save 却成功**）——单线程永不复现 | 给 `onnx_embed._get_cached_ef()` 加**双检锁**；并发首次导入第三方库一律要加锁 |
| `get_collection()` 未传 EF | 查询报 `expecting 1024, got 384`（Chroma 用默认 MiniLM） | **必须显式传 `embedding_function`** |
| `col.get(limit=N)` 取内部顺序 | 取样全是 1 字记忆/短边（重建按长度升序） | 取样必须带 `where` 过滤 |
| 系统代理开着但代理程序没跑 | pip/uv 全失败（`WinError 10061`） | `pip install --proxy "" -i <国内镜像>`；**不动注册表 ProxyEnable** |
| PG 原生中文全文检索 | `show_trgm('显存优化')` = `{}`；`to_tsvector('simple',中文)` 整串一个 token | 路线：Python 侧切词（1/2-gram）→ `tsvector` + GIN，或向量检索为主 |

## 十一、回滚

| 场景 | 操作 |
|:--|:--|
| 切了 PG 想回 Chroma | 删除 `BOSHI_BACKEND` 环境变量 → 重启进程 |
