## 1. 问题：切 PG 之后少了一条腿

v7.0 把存储从 Chroma 切到 Postgres + pgvector 后，`pg_bridge.search_memory()` 的实现是：

```sql
SELECT ... ORDER BY embedding <=> %s::vector LIMIT %s
```

单路纯余弦。而 Chroma 时代的检索是「向量 + 关键词」双路。后果是**字面特征召回整体失效**：

| 查询意图 | 纯向量实际返回 |
|:--|:--|
| `tensor-split 显存` | 「显存放不下怎么办？」（泛泛而谈，无 tensor-split） |
| `ComfyUI 显存不足` | 「跑之前，先查看进程…」（无关） |
| `Qwen3.6-27B QLoRA` | `qwen3.8-27b-q80`（型号被语义吃掉，金标 doc 排到第 116 名） |

原因不是向量模型差，而是 embedding 对「型号 / 端口 / 参数名 / 数字」这类**低语义高区分度**的 token 天然模糊：
`Qwen3.6-27B` 与 `Qwen3.8-27B` 在向量空间几乎同义。这类特征必须靠字面通道。

## 2. 设计

三层，全部在 `pg_bridge.py` 内，无新依赖（不用 reranker、不用 jieba、不引 BM25 库）。

### 2.1 分词

- `_kw_tokens(query) -> [(token, weight)]`：查询侧，带权重。
  - ASCII 型号/路径/端口：3.0
  - 数字（≥2 位）：2.5
  - 中文连续段（整段）：3.0；段长 ≥3 时另出全部 bigram：1.0
  - `len < 2` 丢弃；去重保首现；截断 16 个 token
- `_doc_tokens(text)`：文档侧索引 token（中文整段 + bigram，单字不入索引）。
- `_norm_ascii(tok)`：去掉 `_ - . / ,`，使 `IQ4_XS` ≡ `iq4xs` ≡ `IQ4-XS`。

### 2.2 关键词通道（进程内 BM25）

语料只有 ~6000 条、平均 323 字符（≈119 tokens），全量入内存建倒排完全可行：

- `_kw_index(c, cond, params)`：`docs=[(id, content, meta, dl)]` + `postings={token: [(doc_idx, tf)]}` + `avgdl`。
  - 失效条件：`count(*)` 或 `max(created_at)` 变化，或超过 `_KW_TTL=180s`
  - 缓存：`_KW_CACHE` 键 `(cond, tuple(params))`，上限 4 份，`_KW_LOCK` 保护
- `_kw_channel(c, toks, k, cond, params)`：
  - BM25：`idf = log(1 + (N - df + 0.5) / (df + 0.5))`，`score = Σ w·idf·tf/(tf + k1·(1 - b + b·dl/avgdl))`，`k1=1.2`、`b=0.50`
  - 协调因子 coord：`scores *= 命中主词权重 / 主词总权重`（主词 = `w >= 2.5`；bigram 不进分母）
  - 输出两个分数：`kw`（相对 top1，仅供展示）、**`kw_abs`**（绝对 idf 加权覆盖率 ∈ [0,1]，可跨文档比较 —— 融合用它）

**`_kw_abs()` 的两个补丁（都踩过坑）**：

1. **原文归一化**：`low_n = _norm_ascii(low)`，判定 `tok in low or tok in low_n`。
   缺这句时，库里写 `IQ4_XS` 的文档在 `IQ4XS` 查询下判零命中，整段排序崩掉。
2. **长度阻尼**：`cov /= 1.0 + _KW_LENB * max(0, dl/avgdl - 1)`，`_KW_LENB = 0.5`。
   不加时「如实回答，分三层说…」这类长文靠零星 substring 命中霸榜。
3. 中文主词（≥3 字）做 bigram 部分信用：`_KW_PARTIAL + (1-_KW_PARTIAL)·m/grams`，`_KW_PARTIAL = 0.85`。

### 2.3 融合

```python
# _score_merge
f = (wv*(1 - dist) + wk*kw_abs) / (wv + wk)     # wv=0.45, wk=0.55
score = 1 - (0.60 + 0.40*min(f, 1))             # 单调压到 0.6~1.0
```

- 只被关键词通道捞到的文档，`_cosine_for_ids()` 批量补算真实余弦（否则 v=0，白占便宜）。
- `_rrf_merge`（名次融合 `1/(60+rank)`）保留可切，但**默认不用**：实测会埋掉「单通道第 1」——
  「退休 养老金」金标 vec#1 但 kw 零命中（1/61=0.0164），被「两通道各 ~5 名」的文档（2/65）压出 top5。
- `_has_anchor(query)`：`[A-Za-z][A-Za-z0-9_.+\-]{1,}|\d{2,}`。`auto` 模式下无锚点 → 纯向量。

## 6.1 2026-10-19 常驻进程检验（新增已知问题）

- **Ekko Studio 桥是进程内 AgentPool**（`bridge_pool.py` 的 `class AgentPool` / `class AgentSession`），
  会话不换进程 → 新开聊天**不会**重载模块；Ekko 侧吃到 P1 必须重启 App / 桥。
  opencode 相反：每会话 spawn 新 MCP，新会话天然是新代码。
- **每个进程独占一份 bge-m3**：`onnx_embed.py:85` 是
  `ort.InferenceSession(str(ONNX_FILE), providers=["CPUExecutionProvider"])`，纯进程内推理。
  已有检索行为的 MCP 进程 RSS ≈ **808MB**，未检索的 ~96MB（惰性加载，`pg_bridge._ef()`）。
  多入口常驻时内存线性叠加 —— 需要共享嵌入服务，但那是独立于 P2 的工程。
- **MCP 进程无回收**：实测 2026-10-19 12:31→12:45 内 opencode 连开 6 个 MCP 进程无一退出，
  8 个常驻合计约 1.2GB。排查方向在 opencode 侧生命周期，不在 boshi 侧。

## 7. 与 P2 的关系

P1 只补「怎么找」。写入侧仍把整段助手回复 `asst[:800] + "…"` 直接存成一条记忆
（`plugins/boshi/__init__.py:645-646`），导致：

- 1305 / 6035 条（≈71% 的 `assistant_conclusion`）撞上 800 字符墙，尾部信息被物理截断。
- 截断文本会产生「假匹配」：`[2026-07-02] DeepSeek-R1…--tensor-s` 这种半截 token 被 BM25 的 substring
  规则匹配到，是 `tensor-split 显存` 榜首一度跑偏的直接原因之一。

P2 要做的是把「截断式存档」换成「槽位化抽提 + 原文另存」：`statement / subject / files / decisions /
open_questions / reusable_experience / boundary_envs / confidence`，事实层每会话恰好 1 条、经验层 0~N 条设门槛。
搜索质量的天花板在写入侧，不在检索侧 —— 这是对比 PilotDeck 2.0 / Hindsight / Hy Memory 2.0 三篇之后的共同结论。

## 8. P2 落地：规则抽提 v2（2026-10-19）

### 8.1 为什么是规则，不是 LLM 混合

三条真实结论上对照 `slots.py` / `MiniCPM5-2.6B-F16` / `qwen3.5-4b-buddhist-q8_0` 后定稿：**只用规则**。

| 维度 | 规则 | qwen3.5-4B Q8 | MiniCPM5-2.6B F16 |
|:--|:--|:--|:--|
| 耗时/条 | **0.35 ms** | ≈5.3 s（46-52 tok/s） | 1.2-2.8 s |
| 硬事实（flags） | 5/5、1/1 | 6/6、16/16、15/15 | **4/4、0/0、0/0（漏）** |
| `decisions` | 少但逐字 | 0/2 改写、3/3、1/3（**不稳**） | **全空** |
| `statement` | 结构修好后可用 | 好 | 好 |
| 显存/文件 | 0 | 5.32 GB / 4.3 GB | 5.37 GB / 4.7 GB |

否决理由：① 候选池 1,741 条里 **1,124 条（64.5%）是旧 801 字截断**，瓶颈是数据残缺不是抽提质量；② `statement` 只是索引元数据，检索召回走原文向量 + BM25；③ 成本差 1.5 万倍且与 ComfyUI 抢卡。**重议条件**：`statement` 对检索命中率有可测提升 + `decisions` 逐字率 >90% + 离线批时间可接受，三条同时成立。

### 8.2 结构修复（真 bug）

旧 `_sentences()` 先 `re.split('(?<=[。！？；\n])')` 再 `strip(' \t-*#>')`，于是 `## 一、…（结论）` 这种标题被 strip 成正常句子占掉 `statement`；按 `\n` 切句又把「当前状态一句话：」切成独立空引子。基线 `stmt_len_avg` 仅 **38.6**。

v2 改为**先识别标题行、再切块、块内只按句末标点切句**：`_is_heading(raw)`（`#{1,6} ` / 纯粗体无句读 / 短编号项且无句读，且必须**在 strip 之前**判定）→ `_blocks()` 丢标题行、块内行原样保留 → `_sentences()` 块内 `(?<=[。！？；])` 切 → `_statement()` 取首个 len≥24 的句子 → `_clip()` 在标点处截断。

**块内行必须原样保留**：先删行标记再合并会让槽位值不再是原文连续子串（实测严格子串率 **87.2%**）；切块方案下 **100.00%（1472/1472）**。

### 8.3.2 跑通过程中发现的槽位漏抓（已修）

## 9. 槽位该不该进 BM25？A3 对照实验（2026-10-19，结论：不该）

P2 的原始设想是「有 slots 的行，BM25 文档用 `statement + 槽位值` 替代全文」，理由是压缩后更精准、避免长文半截 token 制造假匹配。这一设想此前**从未量化验证**。A3 就是补这次量化。

### 9.1 实验设置

### 9.3 机制：BM25 的长度归一化反过来奖励被压缩的短文档

槽位文本把一条 1,500–2,000 字的 assistant 结论压成 `statement + 槽位值`（1,880/6,108 行 doc_text 不到原文一半，部分只剩一两百字）。BM25 的 `dl/avgdl` 归一化因此**奖励**这些短文档：同样命中「截断」「4096」这些词，短文档得分更高；三十来字的用户小问天然最短，直接被顶到第一。这层压缩对排序是净负收益，不是正收益。

guard 0.6 / additive 两种变体都只是**打平** baseline（15–14/16、4.50/5），没有任何一条 query 变好 —— 说明槽位文本对 BM25 的贡献 ≈ 0，它现阶段的正确用途是**元数据**（留给 P2+ 的字段级匹配），不是排序文本。

## 10. 检索质量的绝对度量：35 条 gold 评测（A5/A6/A7，2026-10-19 夜）

### 10.1 为什么必须换判据

A3/A1 用的判据是「top1 是否换人」，量的是**稳定性**，不是**正确性**。A5 测出当前索引 top1 只有 60% 正确——在 top1 本身六成对的前提下，"top1 相同 11/16" 既不能证明变好也不能证明变差。故补一套**有 gold 的绝对度量**：判据从"答案换没换"改成"答案有没有被捞到前 N"。

### 10.2 评测集构造

`~/.boshi/eval/cases.py`：35 条 `(query, gold_id8, anchor)`。gold 取自各 profile 的 `assistant_conclusion` / `troubleshooting` / `project` 条目，`anchor` 是该条必须**逐字包含**的字面串（`0x384`、`22528`、`upload_state`、`5165`…）。`eval/check_gold.py` 逐条核对「存在 + `is_latest` + anchor 命中」，当前 **35/35 全过**。

**踩过的坑（指标全错的假象）**：首次评测忘了传 `scope`，`search_memory` 默认按当前 profile 过滤（`pg_bridge.py:388` `_default_scope`），跨 profile 的 gold 直接不可见 → auto top1 只有 37%、纯向量 8.6%。**评测必须显式 `scope="all"`**，否则量的是过滤条件不是检索质量。

### 10.3 结果（`top_k=5` → `k_each=20`，即每通道 20 候选；scope=all）

| 模式 | top1 | top3 | top5 |
|:--|:--|:--|:--|
| **auto**（加权分融合） | **21/35 = 60%** | 30/35 = 86% | 32/35 = 91% |
| rrf | 12/35 = 34% | 26 | 29 |
| vector（纯向量，回滚态） | 6/35 = 17% | 10 | 11 |

三点结论：

1. **融合是真有效的**：auto 的 top1 是纯向量的 3.5 倍。P0/P1 这条线站得住。
2. **rrf 明显弱于加权分融合**（34% vs 60%）——线上默认 `auto` 的选择被 gold 数据证实，不是口味问题。
3. **纯向量 top1 只有 17% 不是嵌入的锅**：实测 query 与 gold 的余弦 **0.795**，全库平均 **0.610**。真正原因是库里存在大量**同主题的用户提问**，对"提问式 query"来说它们在语义上比"结论"更近。top1 掉的是**排序层**而非**召回层**（top5 也才 11/35，说明确实排得靠后）。

### 10.4 A6 角色先验：无效，落档不采纳

针对 10.3 第 3 点的直接修法：查询是问句时，对 `role='user'` 的候选加"池内跨度 × δ"的距离惩罚。δ ∈ {0.5, 1.0, 1.5, 3.0}，也试过"不限问句、全部施加"和"额外罚 `topic='conversation'`"：

- top1 **21/35 一条不动**
- 只有 2~3 条 gold 从第 4 名升到第 3/2 名（`c6db5b3f`、`91492b69`、`e83a096c`）

**不采纳**：换不动 top1 的排序改动，收益不抵"检索语义变更"的回归风险。

### 10.5 A7：top_k 敏感性——根因是「池污染」，已修并复测通过

同一批 35 条 query，只改 `top_k`（`k_each = min(max(top_k*4, 20), 100)`）的原始表现：

| top_k | top1 | top3 | top5 |
|:--|:--|:--|:--|
| 5 | 21/35 (60%) | 30 | **32** |
| 10 | 21/35 (60%) | 27 | 31 |
| 20 | 21/35 (60%) | 26 | 29 |
| 50 | 21/35 (60%) | 26 | 29 |
| 100 | 21/35 (60%) | 26 | 29 |

top1 恒定，但 **top3/top5 随请求条数变差**——同一查询「要 5 条」和「要 20 条」，第 3~5 名会变。

**先验证过的错误假设**（留档，避免以后重走）：以为是「截断尺子（原始 BM25 分）与融合尺子（`kw_abs`）不是同一个量」，于是把关键词通道改成按 `kw_abs` 排序后截断。结果 k=5 时 top3/top5 **降到 27/29**（比原 30/32 更差）——说明方向错了。

**真实机制**：融合是**绝对分**加权（`pg_bridge.py:954` `_score_merge`：`f = (wv*(1-dist) + wk*kw_abs)/(wv+wk)`，没有池内 min-max 归一），所以池子越大**只会加入**新文档，不会重排已有文档。而 BM25 原始分的长尾是噪声：这些文档 `kw_abs` 中等（0.2~0.3）、余弦低，单通道都不该进前 5，但池子一到 80 条就挤进融合池、把真 gold 顶出前 5。
→ 问题在**池子大小**，不在排序尺子。附带解释了 §9.5 的一个疑点：`BOSHI_BM25_B` 从 0.50 调到 0.20 结果逐位不变，因为**融合吃的是 `kw_abs`**（由 idf 覆盖率 + `_KW_LENB` 决定），`B` 只影响原始 BM25 分，而原始分只用于池内排序；池子只有 20 条时，改 `B` 没让任何一条候选的进出发生变化。

**修法**（`pg_bridge.py:583` `_KW_POOL_CAP`，默认 20，`BOSHI_KW_POOL_CAP=0` 可回滚旧行为）：
关键词通道候选数**与 top_k 解耦，固定 20 条**；向量通道仍随 `k_each` 增长（top_k=100 时向量 100 条、关键词 20 条，融合池最多 120）。

复测（`eval/a7_poolsize.py`，默认参数）：

| top_k | 5 | 10 | 20 | 50 | 100 |
|:--|:--|:--|:--|:--|:--|
| top1 | 21 | 21 | 21 | 21 | 21 |
| top3 | 30 | 30 | 30 | 30 | 30 |
| top5 | 32 | 32 | 32 | 32 | 32 |

五档完全一致（top5 漏召仍为 `70cd3d35` `d2ccef88` `0ce918be`）。验收线 *top1 ≥ 21/35 且 top5@k20 ≥ 32* **达标**，且 k=5 基线未退化（21/30/32）。

延迟（本机热态，6 条代表 query 各跑 2 轮）：`top_k=5` 56 → 55 ms，`top_k=20` 62 → 55 ms（少算 60 条长尾的 kw_abs，略快）。

**代价（如实记录）**：`top_k > 20` 时关键词通道只贡献 20 条候选，理论上存在「第 21 名之后的关键词强命中」拿不到的情况；当前评测集里没有这种样本（35 条 gold 的 top5 召回不受影响）。要再接大 top_k 场景（如批量导出），应重跑 A7 并把 cap 调到 50/100 比较。


## 11. P2+ 字段级匹配：查询里的字面量抬升（2026-10-20，默认开）

### 11.1 动机与前任实验的教训

§9 的 A3 已经证明**槽位文本整篇替换 BM25 文档是净负收益**（长度归一化奖励短文档）。P2+ 换了问法：不碰文档，只问**"query 里出现的字面字段（端口 / 版本 / 开关 / 路径），候选的同一字段是否也有"**。这类值（`8199`、`0.1.44.1`、`--tensor-split`、`D:/llama`）的匹配是精确的，不受文档长度、分词断裂影响。

### 11.2 实现（`pg_bridge.py:1046-1130`，`_field_match`）

- 对 query 跑一次 `slots.extract()`，取 `_FM_KEYS` 里的字段；候选侧按 id 批量 `SELECT id::text, slots FROM boshi.memories WHERE id::text = ANY(%s)`，`slots IS NULL` 的历史行**现场从 content 抽**（不为检索写库）。
- 命中判定 `_fm_hits`：同字段**双向包含**即命中，值先 `_fm_norm`（小写、去空白、去首尾标点）；`_fm_norm` 只做形态归一，不改字。
- 抬升：`gain = min(_FM_MAX, _FM_STEP × Σ权重)`，写回 `it["score"] = 1 - min(1, sim + gain)`，并记 `field_hits` / `field_gain` 便于后续排查。任何异常直接退回原排序（检索永不因本特性失败）。
- 候选池：`pool_k = top_k × _FM_POOL(3)`，让"本来没进前几名"的字面命中还有机会被抬进来；`BOSHI_FIELD_MATCH=0` 时 `pool_k = top_k`，代码路径与 P2+ 之前等价。
- **槽位仍不进 BM25 文档**（`_doc_text` 口径不变，`BOSHI_KW_DOC=content`）。

参数默认：`_FM_STEP=0.10`、`_FM_MAX=0.30`、`_FM_POOL=3`、`_FM_W={ports:1.0, versions:1.0, flags:1.0, files:0.8, numbers:0.4}`。

### 11.3 `numbers` 被踢出默认集合（扫描结论）

`scratch/sweep_field_match.py` 在 auto 模式下扫 8 组（含 `numbers` 的 5 字段 × 步长 .10/.15/.25/.40；去掉 `numbers` 的 4 字段 × .15/.25/.40；只留 ports/versions/flags 的 lit3）：

| 组合 | top1 | top3 | top5 | 名次变动 |
|:--|:--|:--|:--|:--|
| baseline（fm off） | 20 | 30 | 32 | — |
| 含 numbers，四档步长 | 20 | 30 | 32 | 都是 3 条：`7d944c53` 1→2、`e79e3fe9` 3→1、`08e4fa8e` 3→2 |
| 不含 numbers（三档） | 20 | 30 | 32 | **0 条** |
| lit3 | 20 | 30 | 32 | **0 条** |

两个事实：① 35 条 gold 里**没有一条 query 带 ports/versions/flags/files 字面量**（四类命中数为 0）——所以 A5 对这四个字段完全不敏感；② 唯一触发的是 `numbers`，而它是净 0（1 条上升、1 条下降），且 `218`/`24`/`5` 这类数字跨语境复用，属歧义字面量。

→ 默认集合改为 **`ports, versions, flags, files`**；`numbers` 可用 `BOSHI_FM_KEYS=ports,versions,flags,files,numbers` 显式打开。

### 11.4 定向验收：A8（40 条字面量 gold）

A5 无法评价本特性（见 11.3），故补 `eval/a8_field_gold.py`：从库里挑 `slots` 含 `ports`/`versions`/`flags` 的记忆（端口 14 条、版本 14 条、开关 12 条），用「**字面量 + 该条内容里的 2~3 个关键词**」拼成查询（语义弱、字面量强，正是本特性的目标场景），gold = 该条记忆 id。这批 query 天然偏向"字面量必须起作用"，因此它测的是**目标人群上的增益**，不代表全量流量收益。

| 模式 | top1 | top3 | top5 |
|:--|:--|:--|:--|
| fm off | 25/40 (62.5%) | 32 | 36 |
| fm on（4 字段） | **29/40 (72.5%)** | **33** | 36 |

**+4 top1、+1 top3、top5 不变**，且与"含 numbers 的 5 字段版"结果完全相同（29/33/36）——再次说明增益来自高精度四字段，`numbers` 只贡献噪声。

同时 A5 回归（35 条真 query）：auto **20/30/32，与 fm off 逐条一致**（`logs/a5_p2plus_fm4k.json`）；rrf 12/27/29、vector 8/12/13（纯向量模式 top1 6→8）。

### 11.5 为什么要说清 A5 的 21→20

上一版基线是 **21**/30/32，本轮 fm off 测得 **20**/30/32。逐条 diff 只有一处：`55cc3251` rank 1→2，与 `8055b300` 互换，两条正文前缀完全相同（都是「P4进度(218四期中医知识库): tensor版32B-VL服务验收通过…」）——**近似重复条目的名次互换**，不是语义退化。fm 关闭时代码路径与 P2+ 之前等价（`pool_k=top_k`、向量池 `max(k_each,20)` 不变），差异来自库在 12 小时内的新增写入改变了 df 与向量池竞争。检索指标跨天比较必须重跑 baseline，不能拿昨天的数字当今天的分母。

### 11.6 成本与开关

| 项 | 值 |
|:--|:--|
| 延迟 | 35 条 query 各跑 2 轮：fm off 71.7~73.7 ms/q，fm on 73.6~73.7 ms/q → 开销 ≤2 ms（<3%） |
| 额外查询 | 每次检索 1 条 `id = ANY(...)` 的 slots 查询（≤ =3×top_k 个 id）+ query 侧一次 `extract()`（纯正则） |

| 缺槽位时 | 候选侧现场从 content 抽，不需要先回填 |

### 11.7 结论

在**真 query 上净中性**（0 涨 0 跌，延迟 +2ms）、在**字面量 query 上 +10 个百分点 top1** → 开默认。若日后线上发现数字类误抬升，第一步先把 `BOSHI_FIELD_MATCH=0` 关掉再定位，不要动 BM25 口径。

### 11.9 活体验证发现的 query 侧盲区（2026-10-20 下午，已修）

**症状**：P2+ 开默认后拿真实 query 实跑，`field_hits` **全是 None**——等于功能没生效。

**根因**：`slots.py` 的抽提器是为**长文档**设计的，端口规则只扫「关键词**之后**」同一分句（`_ports()`，`slots.py:183-191`）：

| 写法 | `slots.extract` 结果 |
|:--|:--|
| `端口 8199 监听了吗` | `ports: ['8199']` ✅ |
| `8199 端口 llama-server 怎么配`（人真实提问） | 只有 `boundary_envs`/`statement`，无 ports ❌ |

A8 的 query 是「字面量 + 关键词」拼的，而字面量本身抄自 slot 值 → **天然绕过抽提器盲区**，所以 A8 看不到这个问题。教训：定向验收集必须用*人真实会怎么说*来写 query，不能从要验证的字段值反推。

**修法（`pg_bridge.py`，只改 query 侧，不动文档抽提语义）**：新增 `_fm_query_extra(query)` + `_RE_PORT_LOOKAHEAD`
```python
_RE_PORT_LOOKAHEAD = re.compile(
    r"(?<![\d.])(\d{2,5})(?=[^\d。；;，,\n]{0,6}(?:端口|端口号|监听|port|PORT))")
```
数字在关键词前 6 字内即认端口，再按 `1..65535` 过滤。`_field_match` 里与 `sm.extract(query)` 的结果合并（仅当 `ports` 在 `_FM_KEYS` 内）。不改 `slots.py` 的理由：文档侧「端口 8199」早已抽全，改抽提器要重跑全量回填，blast radius 远大于收益。

**修后实测**（`scope=all`，同一批真实 query）：

| query | 修前 field_hits | 修后 |
|:--|:--|:--|
| `8199 端口 llama-server PE 反推怎么配` | 0 条 | 3 条（`ports`，gain 0.10） |
| `8648 端口那个 web ui 是啥` | 0 条 | 2 条 |
| `8199 端口` | 0 条 | 3 条 |

回归：A5 `20/30/32`（与修前逐条一致）、A8 `25/32/36 → 29/33/36`（与修前一致）、`tests.test_field_match` 11 条全过（IP 不算端口、`131072`/`2026-10-20`/`v7.2` 不误抓、越界 99999 丢弃）。

**顺手修的验收脚本 bug**：`eval/a8_field_gold.py` 基线原来用 `os.environ.pop("BOSHI_FIELD_MATCH")` 吃默认值；默认从 0 改成 1 之后基线跟着变成「开」，两栏数字一模一样（29/33/36 vs 29/33/36）差点被当成"零收益"。已改为显式 `= "0"`。**教训：用 pop 吃默认值的基线，在默认值变更后会静默失效。**

### 11.10 4 段版本号：测得该做但暂不做（2026-10-20）

`RE_VER`（`slots.py:46`）最多 3 段：`0.1.44.1` 抽不出。全库 latest 6,160 行实测：**189 行含 4 段数字，slots 里 versions 命中 0 条**；但按 token 去重后 29 个 token 里 **319 次是 IP**（`172.16.0.218`、`127.0.0.1`），非 IP 形状只有 **18 次 / 7 个 token**（`v0.1.40.4`×4、`v0.1.44.1`×4、`10.0.19041.3636`×3 等）。

结论：放开到 4 段必须先排除 IP 形状，而 `0.1.44.1` 与 `1.2.3.4` 在语法上无法区分 → 只能用「有 `v` 前缀」「紧邻 `@`/`版本`」这类上下文规则，收益 18 次、成本是全量回填 + A5/A8 重跑。**记为待办，不在 P2+ 里做**；届时只需加 `v\d+\.\d+\.\d+\.\d+` 这条无歧义规则（`v` 前缀绝无可能是 IP）。

**(2) 线上打点（`pg_bridge._fm_trace`，默认关）**

`BOSHI_FM_TRACE=1` 时，每次 `_field_match` 在**排序前**记一行到 `~/.boshi/logs/fm_trace.jsonl`：

{"ts":"2026-10-20T09:50:52+08:00","query":"端口 8199 怎么配","fields":{"ports":["8199"]},

- 只在 `qfields` 非空（query 真带字面量）时才走到这里，频率低；一次 append，无 IO 压力

- `top1_hit` = 抬升后的 top1 自身是否命中字段；**若 `top1_changed=true` 而 `top1_hit=false`，说明重排逻辑出错**（抬上去的不含该字面量），报告脚本会单列"可疑"

### 11.12 纯中文 query：A5 答不了，另建 A9（2026-10-20）

**(1) 问题**：`pg_bridge.py:1252-1256` 的 auto 门（`mode == "auto" and not _has_anchor(query)` → 跳过关键词通道）会让**纯中文自然语言提问**只用向量通道。要不要放开，需要度量「放开后有没有用」。

**(2) A5 回答不了**（`scratch/a5_fusion_modes.py`）：A5 的 35 条 query **全部** `_has_anchor=True`（带锚点 35 / 纯中文 0），auto 与 score 逐条 35/35 相同。**验收集的构造决定了它能回答什么问题**——这是 A8 那条方法论坑的翻版。

顺带杀掉一个假信号：总览里 auto 184ms vs score 106ms 看着是 auto 更慢，交叉排序复测（同 8 条 query）`('score','auto')` 得 score 367 / auto 131，`('auto','score')` 得 auto 119 / score 122 → **同进程内每个 query 的第一次调用带冷成本**，模式对比必须交叉排序。

**(3) A9 测集**（`eval/cases_a9.py`，`eval/a9_eval.py`）：20 条 gold × 2 种问法 = 40 条，同一条 gold 配两种问法以消掉「gold 难度」混杂：

- `overlap`：用户凭印象复述、复用原文词
- `paraphrase`：完全换词、只留语义

自检两条（不满足即 exit 1）：① anchor 必须逐字出现在 gold 正文；② `_has_anchor(q)` 必须为 False。首跑就抓出 `b74d2c87` 的 anchor「拉扁」不在正文（原文是「视频拉伸了原图，扁了」），改成「扁了」后 40 条全过。

**(4) A9 v1 结果**（`logs/a9_v1.json`，scope=all，gold 名次 top1/top3/top5）：

| 组 | auto | score | vector |
|:--|:--|:--|:--|
| overlap (n=20) | 0 / 2 / 6 | 0 / 2 / 6 | 0 / 2 / 6 |
| paraphrase (n=20) | 0 / 1 / 1 | 0 / 1 / 1 | 0 / 1 / 1 |

**40 条逐条 auto == score，一条不差**。两层含义：

1. 纯中文无锚点 query 的**绝对召回极差**（top1 0/40），瓶颈不在关键词通道；
2. 「放开通道」在当时对 top5 **没有可测影响**——但机制未明（kw 零命中？被阈值砍？被余弦压出榜？），不能就此下结论（见 §11.13）。

**(5) 软命中口径**（`scratch/a9_soft.py`）：记忆库把同一段对话切成多条近重复记录（A9 的 20 条 gold 里只有 7 条有 `session_id`，同一话题常有 3~4 条近文），用 record id 判分会低估检索质量。故另算两档可接受命中：`soft5` = top5 里有同 session_id 的兄弟切片；`dup5` = top5 里有与 gold 余弦 ≥ 0.92 的近文。基线（auto=vector）：overlap soft/dup 11/20、paraphrase 6/20。

### 11.13 coord 退化：纯中文上关键词通道是静默死路（2026-10-20，已修）

**(1) 探针**（`scratch/a9_kwprobe.py`）：8 条纯中文 query 的 `_kw_channel` 候选**全部 0 条**。再往下查，`_kw_tokens`（`pg_bridge.py:646-652`）把整段连续汉字当成**一个 3.0 权重的主 token**（如 18 字整句），bigram 只取前 6 个（`range(min(n-1, 6))`）；整句几乎不可能作为 token 存在于 postings（df=0）。

**(2) 归零链条**（`scratch/a9_coord_zero.py` 复算证实）：

```
整句主 token df=0 → hits[idx]["cov"] 不累加（pg_bridge.py:889-901 只对 w>=2.5 的命中计 cov）
→ pr 全 0 → scores = s * (0 / denom) = 0
→ top = ranked[0][1] or 1.0 → rel = 0 < _KW_MIN(0.05) → 候选全灭
→ search_memory 侧 kw_items 为空 → 退回纯向量
```

实测：「群晖硬盘显示已损毁但检测是好的怎么办」raw BM25 **295 候选**、gold `7f6c4aba` 排 #2，coord 后**非零 0/295**；「显存不足怎么办」raw 897 → coord 后 0/897；只有整句恰好等于库内 token 的「显存不足」幸存（coord 后 6/594）。

**后果**：为 CJK 设计的 `_kw_abs` 部分信用（`pg_bridge.py:843-847`）在 CJK-only query 上是**死代码**——候选已在上游被丢光，根本走不到它。

**(3) 修复**（两处，默认开）：

- **coord 退化保护**：`main_hit_n`（主 token 里库内真有的个数）计数；`main_hit_n == 0` 时不施加 coord，保留原始 BM25 分。可证明的 no-op：只要有一个主 token 命中就走原分支，故对带锚点查询**逐条不变**（A5 三模式 0/105 变化）。
- **弱证据降权**：`_kw_channel` 给降级候选打 `_weak=True`；`_score_merge` 见到 `_weak` 且调用方未显式传权时，把 `(wv, wk)` 从 `(0.45, 0.55)` 降到 `(0.70, 0.30)`（`BOSHI_KW_WEAK_WV/WK` 可调）。理由：只剩 bigram 证据时 `kw_abs` 表达的是「零星 2 字切片对上」，与整词命中不可同日而语；等权融合实测会把 gold 挤出 top5。`_weak` 在 `_score_merge` / `_rrf_merge` 出口 `pop` 掉，不外泄给调用方。

**(4) 验收**（A9 v2，`logs/a9_v2.json`，源码态无 monkeypatch）：

| 组 | auto（门关） | score（门开） | vector |
|:--|:--|:--|:--|

| paraphrase top1/top3/top5 | 0 / 1 / 1 | **1 / 1 / 2** | 0 / 1 / 1 |

- 中间态对比（`scratch/a9_option_c.py`）：只做 coord 保护不做降权 → overlap 4/8/10、paraphrase 1/1/1，且 paraphrase 有一条反向（`56d59b74` 被 bigram 噪声挤出 top5）。降权后 overlap top3 8→9、top5 10→12，paraphrase top5 1→2，**三个口径全面不劣**。

**(5) 门开不开还没定（政策项，待乐之拍）**：修复只让 score/rrf 模式在有主 token 命中的查询上等价于现状、在纯中文查询上不再静默失效；**auto 门本身未动**（默认融合仍是 auto，所以线上行为对带锚点查询零变化，对纯中文查询仍走纯向量）。

门开的收益与风险（`scratch/a9_negation_probe.py` 定性 4 例）：

### 11.15 P3 写入侧版本化契约：`save(..., upsert=True)`（2026-10-20 10:53，代码+实测完成）

### 11.16 P3 事实层落地：`sync_turn` 门控写 `session_fact`（2026-10-20 12:01）

**(1) 为什么不「每轮都写一条」**：`task_conclusion` 的两个钩子在本机几乎不触发（§11.15(7)），事实层等于空的 —— 下个会话问「上次那个定下来没有」召回不到。但**无条件**每轮再写一条 `session_fact` 只是把 `conversation` 复制一份，库会被滚脏、检索位被占满。故设计成**门控 + 滚动累积**。

**(3) 滚动累积**：`topic='session_fact'`，正文是「决策 / 待办」两小节的清单：

```
决策：

待办：
- <原文片段>
```

### 11.18 P1③ 经验层落地：零模型、跨会话累积的可复用教训（2026-10-20 22:46）

**为什么补这一层**：事实层（`session_fact`）回答「这一轮定了什么」，但**只在会话内滚动**（`FACT_CAP=10`），会话一结束就沉底。原升级方案里 P1③ 的要求是「经验/程序性记忆须一等公民且带适用条件」——之前只有 `slots.py:318-321` 抽出来的两个**文本片段**（`reusable_experience` / `boundary_envs`），既没有独立存储、也没有价值门槛与出处链，等于没收。本层是这项的补课。

**存储：复用 `boshi.memories`，`topic='experience'`，不建新表。** 理由：经验行天然继承现有的向量/关键词检索、`is_latest` 版本化与时间线查询；独立通道只是在排序前把它们单独捞一遍，不需要新 schema。去重键 `meta.exp_key = sha1(norm(entry))[:16]`，`norm()` 只压空白、去首尾、去尾部标点——**不改正文其余字符**，所以同一句话换个空行仍是同一 key，而「差不多」的两句话不会误合并。

**价值门槛（两级，全规则、零模型）**

| 级 | 判据 | 为什么 |
|:--|:--|:--|
| A 质量门（写入即判） | 长度 12–300 字；非问句（不以 `？`/`?` 结尾）；非元话语（不含「你觉得/要不要/谢谢/请问」等）；**且** 有三者之一：① `slots` 里的技术锚点（`files/commands/ports/versions/flags/numbers` 任一非空）② 具名物标识符 `_IDENT_RE`（如 `local-rag-kb-querying`、`CUDA`）③ 因果/条件词（`_CAUSAL`：因为/所以/否则/必须/实测/坑…） | 只靠「有因果词」会收进「代码应该写得干净一点」这类观点句；只靠锚点会漏掉「实测过了，别开 MTP」这种无路径的经验。三者取或，恰好把「点到具体东西」和「说清了条件」两种可复用形态都收下 |
| B 复用门（跨会话） | 同 `exp_key` 在 **≥2 个不同 session** 出现 → `status=promoted`；只在一个会话出现留 `candidate`，召回时 ×0.5 降权 | 单靠 A 会把「顺带一提的感想」也收进来；单靠 B 永远收不到第一条。两级合用才既收得住又不被污染。**同会话重复只累加 `hits`，不升级**（否则一轮里说两遍就算「复用」） |

超过 300 字**丢弃而非截断**——截断等于伪造半句，违反原文保真。每轮最多新收 `ROUND_CAP=3` 条（`slots` 每个槽位本身也限 3 条）。

**双向链**：经验行 `meta` 写 `source_fact_ids` / `source_msg_ids`（各上限 8 个，去重追加）；事实行与消息行的 `meta` 回写 `derived_experience_ids`。这样从「这条教训」能查到它出自哪一轮的哪句原文，从「那轮对话」也能看到沉淀出了什么经验——`remember()` 返回到链行数，`link_back()` 负责回写。

**召回：独立通道，零模型打分**
- `experience.recall(query, top_k, profile, scope)`：`score = 命中 token 数 / min(查询 token 数, 8)`；promoted ×1.0、candidate ×0.5；入选门槛 `score ≥ 0.34` **且命中 ≥2 个 token**（中文里单 token 命中几乎等于噪声），或整条查询（≥4 字）作为子串出现直接置 0.8。查询侧 token = 中文 2-gram（去 30 个纯虚词 bigram）+ 英文小写词。
- 全量取本 profile ≤300 条经验进内存打分，45s 进程内缓存（`_CACHE`，写入时 `gen` 自增失效）——经验体量天然小，比再走一次向量检索便宜且可解释。
- `pg_bridge.search_memory` 在 `_session_expand` 之后、`include_graph` 之前注入（`pg_bridge.py:1377-1419`）：只占 `top_k` 里 1 个名额（`BOSHI_EXP_SLOTS`），**未转正且 score<0.8 的不占名额**；score 转成距离语义 `1.0-score`（与 `_row_to_item` 的「越小越近」一致）后置顶。
- 若该经验行已被向量/关键词带上来：**不重复占位**，只把 `"experience"` 追加进它的 `metadata["channels"]`——让「经验层也认可了它」对调用方可见（这一条是冒烟时发现并改的：原实现直接 `continue`，导致 top1 明明就是经验行却标着 `channels=None`）。
- `boshi_core.search` 补 `if "experience" in ch: tag="experience"`，否则 `tag` 判定会把单通道经验行误标成 `vector`。

**接线位置**：`plugins/boshi/__init__.py` 的 `sync_turn` 第 4 步（事实层之后，第 870 行起），与事实层同级、**不受 `if sid_fact:` 门控**；`u_msg_id`/`a_msg_id`/`fact_row_id` 由三处 `save()` 的返回值取出（原代码丢弃返回值，为此改成 `_r = self._core.save(...)`）。整段包在 `except Exception: logger.debug` 里——经验层是增强项，坏了不许拖累主写入。开关 `BOSHI_WRITE_EXPERIENCE=0`。
