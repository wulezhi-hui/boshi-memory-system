## 1. #1 数值冲突：暴露，不裁决

**缘起（实测）**：写入「云闸的开闸宽度当前设定为 40 层」，后写入「已调整为 100 层」；查「现在设定多少」时旧值仍排 top1（rr 6.88 / conf high），新值第二（rr 5.26）。
**为什么旧的折叠逻辑没兜住**：`_fold_value_changes` 的判据是「去掉数字后整句同构」，而「当前设定为」vs「已调整为」措辞不同 → 永不配对；`detect_conflicts` 要求槽位交集，且只在离线可调。

**做法（只做两件事）**：
1. 给冲突双方双向打标记：`conflict=True`、`conflict_role`（newer/older）、`conflict_with`、`conflict_values`；
2. 把较新的一条排到较旧之前——**只调位置，`score` 不动**。

**边界**：不自动判定真伪、不写库、不写 `is_latest=false`。已 `is_latest=False` / `superseded` 的旧版本跳过，不重复标。

**判据与开关**（全部可调/可关）：

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `BOSHI_CONFLICT_EXPOSE` | `1` | `0` 整体关闭 |
| `BOSHI_CONFLICT_COS` | `0.88` | 两条正文余弦阈值（同 topic 且数值互斥才比） |
| `BOSHI_CONFLICT_MIN_GAP` | `60`（秒） | 时间戳差太小不算「新旧」 |

**函数**：`_value_tokens()`（量值集合，`{("40","层")}`）、`_doc_cos()`（只对候选对算，失败返回空 → 降级为不标）、`_mark_value_conflicts()`。

## 4. #4 删除三态契约

```python
{"success": bool, "status": "deleted" | "not_found" | "error",
 "deleted": memory_id, "rows": int | None}
```

| 后端返回 | 契约 |
|---|---|
| 异常 | `success=False, status="error", error="ExcType: msg"` |
| `None`（后端不报行数） | `success=True, status="deleted", verified=False`（无法验证存在性，但已发出删除） |
| 负数 | `success=False, status="error"` |
| `0` 行 | `success=False, status="not_found"` |
| `>0` 行 | `success=True, status="deleted", rows=n` |

**为什么**：「删了」「本来就没有」「后端报错」三态必须分得清——此前 5 条测试残留被一次全 `False` 的批量删除误判成「清理完成」。CLI `cmd_delete` 与 `chroma_bridge.delete_memory` 同步按此约定返回行数。

## 6. #6 图谱边：关系原串 + 去重

### 6.1 问题 1：原串被归一吞掉
`graph_edges.relation` 此前落库是**归一值**（自定义关系一律 `related`），读侧也照抄 → 「跨域引用」这类关系的语义永久丢失。

- **写侧**（`pg_bridge.add_memory` 边分支）：`rel = meta["relation_raw"] or meta["relation"] or meta["rel_type"] or ""`，`relation` 列存**原串**。
- **读侧**：新增常量 `_EDGE_META_SEL`，一次提供四个键：
  - `relation` = 原串（对外主键，老读者照旧可用）
  - `relation_raw` = 原串
  - `relation_norm` = `CASE WHEN relation IN ('updates','extends','derives','related') THEN relation ELSE 'related' END`
  - `rel_type` = 与 `relation_norm` 同值（兼容老读者）
  
  替换原 4 处内联 `jsonb_build_object('type','relation',...)`：`_search_edges`、`search_memory(include_graph=True)` 段、`get_by_id`、`get_all_relations`。
- **边文本**：`knowledge_graph.py:176`
  ```python
  content=f"{from_id} --[{rel_raw or rel_type}]--> {to_id} [...]"
  ```
  该 content 会被嵌入并展示给模型；写归一值等于正文里也丢掉原意。
- `knowledge_graph.query()` / `get_graph_context()` 读 `relation_raw` 优先，`relation_norm` 供推理用（4 类语义）。

### 6.2 问题 2：去重在 PG 后端完全失效
- PG 把边单独存 `graph_edges`，读回 metadata **没有 from_id/to_id** → 原判断 `em.get("from_id")==from_id and em.get("rel_type")==rel_type` 恒不命中；
- 且 `get_all_relations()` 带 `LIMIT 10000`，边表 84578 行 → 超窗口的边永不去重，每次写入还白拉一万行。
- **实测**：同一对实体连续 `add_edge` 两次 → `graph_edges` 出现 **2 行重复边**。

**修复**：新增 `find_edge(entity_a, entity_b, relation_norm=None, relation_raw=None)`

```sql
SELECT id FROM boshi.graph_edges
 WHERE entity_a = %s AND entity_b = %s
   AND (relation = %s OR (relation IN ('updates','extends','derives','related') AND relation = %s))
 LIMIT 1
```
- 有 `relation_raw` → 原串精确匹配（第二项兜住「原串是 4 类标准关系」的等价情况）；
- 无 `relation_raw` → 按 CASE 归一值比；
- 异常返回 `""`（去重失败退化为新建边，不阻断写入）。

`chroma_bridge.py:1035 find_edge()` 是同一函数的 chroma 后端版（`col.get(where={'type':'relation'}, limit=20000)` 后内存比对，原串优先），并在 `_PUBLIC_API` 中登记 → `BACKEND=pg` 时自动被 pg 版替换。

`knowledge_graph.add_relation` 去重块简化为：

```python
from chroma_bridge import find_edge
hit = find_edge(from_id, to_id, rel_type, rel_raw)
if hit:
    return hit
```
仅在 `ImportError`/`AttributeError` 时退回单条 `search_memory`（不再拉全表）。

### 6.3 为什么是「原串优先」而不是「归一值优先」
首版按「实体对 + 归一关系」比 → 「引用」与「不同关系」都归 `related`，互相顶掉，**实测少写边**。原串精确匹配后：同一对外，`引用`/`不同关系`/`derives` 三条并存；4 类标准关系原串==归一值，行为不变。

### 6.4 性能
`find_edge` 实测首调 0.107s、后续约 1ms（84k 行未建索引）。按「查≠改」原则**不动表结构**；若边表继续增长到百万级再议 `(entity_a, entity_b)` 索引。

## 8. 已知遗留

1. **热态检索仍在 5~14s**：瓶颈在精排池深 100 + 候选重排，与六项修复无关；会话注入有超时保护会丢上下文，值得单独立项（池深自适应 / 按置信度早停）。
2. **历史边 `relation` 为空**：84578 行里绝大多数是修复前写入的，`relation=''`；读侧 `relation_norm` 会显示 `related`，但原串已不可追回。若要根治需按 content 里的 `--[xxx]-->` 回填（写库操作，需单独确认）。
3. **`_EDGE_META_SEL` 是字符串拼接**：4 处读路径依赖拼接顺序（`... + _EDGE_META_SEL + " AS meta..."`），后续改 SQL 时注意别把逗号位置挪错。
