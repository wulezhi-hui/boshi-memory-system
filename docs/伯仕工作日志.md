## 2026-09-13 — boshi_bridge.py 新增 time_range 命令（DSH 插件桥接层补全）

**操作：** fix（DSH 插件时间感知召回的必需依赖，经用户授权后改动）
**文件：** `boshi_bridge.py`

**详情：**

- **触发**：DSH 侧 `boshi-auto-memory.mjs` 新增"时间感知召回"功能（检测用户消息中"今天/刚才/上午/昨天"等相对时间词，自动走 `boshi_time_range` 查询），但 DSH 插件通过 `boshi_bridge.py` 子进程调用伯仕接口，bridge 原先只支持 4 个命令（save/search/profile/status），`time_range` 报 `unknown command`，导致时间线召回完全静默失效。
- **改动（纯增量，3 处）**：
  1. import 行加 `time_range`（`from boshi_core import search, save, profile, status, time_range`）
  2. 新增 `elif cmd == "time_range":` 分支（约 20 行），解析位置参数：
     - `argv[2]` = since（必填）
     - `argv[3]` = until 或 top_k（按数值大小判断：<1000 视为 top_k，≥1000 视为 until，因 Unix 时间戳远大于 1000）
     - `argv[4]` = top_k（覆盖）
  3. 文件头部加 `sys.stdout.reconfigure(encoding="utf-8")`（修复 Windows 下 GBK 编码崩溃——记忆内容含 ✅ 等 Unicode 字符时 `json.dumps` 会报 `UnicodeEncodeError`）
- **关键坑**：PowerShell 传参时**丢弃空字符串参数**（`python bridge.py time_range 123 "" 5` 实际传入 `[123, 5]` 只有 4 个 argv 元素），导致 until/top_k 位置错位。修复方式：DSH 插件侧改为条件传参（until 为空时跳过该参数），bridge 侧按数值大小自适应判断。
- **回归验证**：
  - `time_range <since>` → 50 条 ✅
  - `time_range <since> <top_k>` → 50 条 ✅
  - `time_range <since> <until> <top_k>` → 5 条 ✅
  - `search` / `save` / `profile` / `status` 不受影响 ✅
- **边界说明**：`boshi_bridge.py` 是 DSH 专用桥接层（位于 `~/.boshi/`），非共享核心层（chroma_bridge/boshi_core/boshi_mcp_server），改动不影响 Hermes 侧。

## 2026-09-13 — DSH 插件 boshi-auto-memory.mjs 修复 3 个 bug + 时间感知召回

**操作：** fix（DSH 侧插件，非伯仕共享核心层）
**文件：** `~/.dsh/profiles/web/plugins/boshi-auto-memory.mjs`（DSH 目录）

**详情：**

- **触发**：Hermes 侧核验 dsh 新插件后发现 3 个真 bug，dsh 自修。
- **Bug 1（致命）**：插件调 `callBridge(['time_range', ...])` 但 bridge 无此命令 → 时间线召回静默失效
  - 修法：bridge 加 `time_range` 命令（见上条日志）+ 插件侧改为条件传参（until 为空不传）
- **Bug 2（误杀）**：`isGraphNoise()` 判定过宽——`s.includes('[')` 把 `[2026-07-04 18:18] 任务: …` 格式的 `state_db_import_milestone` 记忆（384+ 条）全误判为噪声
  - 修法：改为 `s.includes('--[') && s.includes('-->')`（双连字符+方括号+双连字符+箭头同时出现才是图谱边）
- **Bug 3（漏源）**：`isValuableSource()` 白名单把 `conversation`/`session_summary`（实际是 topic 值）当 source 值比对，永远不成立；且漏掉 `state_db_import`（31 条）/ `migration`（5 条）/ `hermes_memory_mirror`（2 条）
  - 修法：改为黑名单模式 `isGraphFragment(meta)`：`meta.type === 'relation'` 或 `meta.source === 'auto_extract'` → 排除，其它全放行
- **时间感知召回（新功能）**：
  - `detectTimeWindow(text)` 检测"刚才/上午/下午/晚上/今天/昨天/本周/本月"，转 Unix 时间戳范围
  - 有时间词 → 走 `callBridge(['time_range', since, [until], '50'])`
  - 无时间词 → 走 `callBridge(['search', content, '15'])`（搜 15 条再截断，对标 Hermes top_k=5+FTS）
  - `systemPrompt` 新增 `boshi-memory-rules` section（告诉模型何时用 `boshi_time_range` 何时用 `boshi_search`）

## 2026-09-13 — v6.5 图谱边隔离：召回噪声 70% → 0%（主身改动）

**操作：** fix + docs（数据层过滤，全链路生效）
**文件：** `chroma_bridge.py`、`boshi_core.py`、`boshi_mcp_server.py` + 新建 v6.5 技术文档

**详情：**

- **触发**：dsh 反馈"记忆存了 12020 条却查不到、用不上"，其诊断指向"自动召回每轮只看 3 条"。主身实测复核后确认：**dsh 的"条数论"药方错，真病根是数据层的图谱边污染**。
- **根因（实测）**：知识图谱自动提边（`source=auto_extract`, `type=relation`）与真记忆**混在同一 ChromaDB collection**、参与同一套语义检索。L2 全库 12020 条中 **relation 占 10260 条 = 85.4%**，真记忆仅约 11%。技术类 query（实体名密集）一旦命中，top_k 名额被边占满。
  - 改前噪声率实测：11 个 query / 30 条召回 → **21 条噪声 = 70%**
  - 时间线同样中招：`time_range(近24h)` 返回 5 条**全是** `PID --[derives]--> ...`
  - 噪声来自 hybrid/vector 检索（边被向量化），**不是** `source=graph` 图谱 BFS 那一路（实测返回 0 条）
- **方案**：在数据层 `chroma_bridge` 默认隔离——新增 `_apply_graph_exclusion()`（默认加 `type != relation`）+ `_where_has_type()`（图谱模块自带 type 条件时白名单放行）；`include_graph: bool = False` 从 `boshi_core.search/time_range` 透传到 MCP 工具 `boshi_search`/`boshi_time_range`。退化路径的 Python 端过滤改用新写的 `_where_matches()`（支持 `$ne/$gte/$lte/$and`，替换原来只认 `type` 相等的简化逻辑）。
- **为什么在数据层而不是各消费侧打补丁**：Hermes 插件、dsh 桥接、MCP、CLI 全走 `boshi_core` → `chroma_bridge`，**一处改全链路受益**，也避免 dsh/主身两边过滤逻辑不一致（这正是之前定的边界原则：共享核心层归主身改）。
- **回归实测（全绿，16 项）**：噪声率 **0%**（改前 70%）│ `include_graph=True` 仍能召回边（能力保留）│ `get_relations()` 返 20 边、`get_all_relations()` 返 10000 边、`kg.search()` 3 实体（图谱模块未误伤）│ CLI/桥接/插件/MCP 四入口全通 │ MCP 9 工具齐全 │ 数据 11973→12086 只增不减
- **副作用（已评估，属修正）**：`profile()` 的 `hot_topic` 变空——因为 `heat` 字段**只存在于图谱边**（非图谱记忆实测 0 条带 heat），改前取到的就是图谱噪声。消费方本就有 `isGraphNoise` 过滤，无感。

## 2026-09-02 — v6.3 插件缓存 TTL 修复（解决 prefetch 8秒超时静默跳过）

**操作：** bug_fix
**文件：** `C:\Users\wulezhi\AppData\Local\hermes\plugins\boshi\__init__.py`
**详情：**
- **背景**：伯仕插件已注册初始化（`registered→initialized→activated`），但每轮对话前 prefetch 不召回记忆。诊断发现 Hermes v0.20.6 升级后 `_EXTERNAL_PREFETCH_TIMEOUT_S = 8.0`，伯仕 ChromaDB + ONNX bge-m3 搜索常超 8 秒，后台线程被静默跳过，且无任何超时日志
- **根因**：`prefetch()` 每轮都走同步 `_core.search()` → 慢；`queue_prefetch()` 写入缓存但 `prefetch()` 无 TTL，首轮无缓存，后续轮次缓存被超时吞掉
- **修复方案**：给缓存加 5 分钟 TTL（300秒），共改 4 处：
  1. `import time`（新增依赖）
  2. `__init__()` 初始化 `_prefetch_time = 0.0`
  3. `prefetch()`：有缓存且 `time.time() - _prefetch_time < 300` → 毫秒级返回，不触发慢搜索；无缓存/过期时同步兜底
  4. `queue_prefetch()`：后台搜索完写入 `self._prefetch_time = time.time()`；失败时清 `0.0`
  5. `shutdown()`：清空 `_prefetch_time`
- **修复后工作流**：
  - 第 1 轮：无缓存 → 同步搜索（慢但生效）→ 后台 queue_prefetch 更新缓存
  - 第 2 轮起：缓存命中 → 毫秒级返回 → 正常注入记忆 → 后台继续更新缓存
- **验证**：语法检查通过（`py_compile.compile`）；不改 Hermes 源码，升级安全
- **文档同步**：`伯仕记忆系统v6.2_技术架构文档.md` → 升级为 `v6.3`，§新增"九、prefetch 缓存机制"
- **后续注意**：若 ChromaDB 查询持续慢于 8 秒，可考虑在 `_prefetch_time` 命中时返回缓存而非空，同时 Hermes config.yaml 中 `memory.external_prefetch_timeout` 可设 30 秒作为兜底（但不推荐，会卡对话）

### 根因分析
1. 查询词 = 当前消息，没有实体联想能力
2. 知识图谱 search() 方法只匹配 KNOWN_ENTITIES 静态列表，动态实体如"微调"不在列表中 → 返回空
3. 向量搜索只看当前消息语义，跨话题相似度不够，相关记忆被淹没

### 解决方案
**功能改进（v6.4）：**
- 新增 `_expand_query_search()` 方法（第307-375行）
- 从主查询结果中提取实体名（正则：大写缩写GPU、数字+字母2080Ti、驼峰命名）
- 用实体名扩展二次查询（最多3次）
- 合并主查询 + 扩展结果注入上下文

**依赖修复：**
- 发现 Hermes Gateway venv 缺少 chromadb（Hermes升级后依赖缺失）
- 修改 install.py：安装时额外安装依赖到 Hermes venv
- 新增 `install_hermes_deps()` 函数，确保插件直接可用
- 添加明确的错误提示，下次部署时自动处理

```
