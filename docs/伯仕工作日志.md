## 2026-10-10 — 重启后 PG 二次死亡：CREATE_NO_WINDOW 隐藏控制台 + 孤儿子进程锁死 pg.log

**操作：** fix｜**改动** `pg_bridge.py`（① 启动标志删掉 `CREATE_NO_WINDOW` ② pg_ctl 报错落文件、不再丢 DEVNULL ③ 启动失败自动定点体检）

**现象**（用户重启电脑后验收时发现）：
- 02:01:48 钩子自动拉起 PG（崩溃恢复用了 26.5 秒）→ **02:02:22 就绪**
- **02:03:04** 一条 `graph_edges` HNSW 查询的后端进程被 **`0xC000013A`** 打死 → postmaster 立即终结全部子进程 → **随即自己也被 `^C` 打死**（pg.log 末尾那个孤零零的 `^C`）
- 之后每次 `pg_ctl start` 都失败，而钩子把 pg_ctl 报错丢进 DEVNULL → 自动拉起日志里只有"拉起失败或超时（90 秒）"（黑盒）

**根因（两条，均有日志证据）**：
1. `0xC000013A` = **STATUS_CONTROL_C_EXIT**（Ctrl+C / 控制台关闭事件）。启动标志写的是
   `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | **CREATE_NO_WINDOW**` —— **`CREATE_NO_WINDOW` 会创建"隐藏控制台"**，postmaster 与控制台事件绑定后，控制台被关闭/收到 Ctrl+C 就被整库打死。**两者同时传时，控制台照样被创建**，`DETACHED_PROCESS` 的"无控制台"语义被抵消。
2. postmaster 死时留下**孤儿 `--forkchild="checkpointer"` 子进程**（父 PID 4448 已死、孤儿仍活着），它继承了 **pg.log 的写句柄** → 之后 `pg_ctl` 打开 pg.log 一律 `Permission denied` → 启动静默失败（pg.log 一行不写，看起来像"什么都没发生"）。

**修复**：

| # | 改动 | 效果 |
|:--|:--|:--|
| 1 | 启动标志改为 `DETACHED_PROCESS \| CREATE_NEW_PROCESS_GROUP`（**删掉 CREATE_NO_WINDOW**），并在代码里写明"绝不可加" | postmaster 真正无控制台 → 免疫 Ctrl+C / 控制台关闭事件 |
| 2 | pg_ctl 的 stdout/stderr 落 `~/.boshi/logs/pg_ctl_start.log` | 启动失败不再是黑盒（实测已抓到 `pg_ctl: could not open log file "J:/pgdata/pg.log": Permission denied`） |
| 3 | 超时分支新增 `_log_ctl_output()` + `_diagnose_start_failure()` | 自动把 pg_ctl 报错 + "pg.log 是否被占用"写进自动拉起日志 |

**验证**：拿**当前真实故障状态**跑新诊断 → 自动拉起日志直接输出
`pg_ctl 输出: pg_ctl: 其他服务器进程可能正在运行; 尝试启动服务器进程` +
`体检: ⚠️ pg.log 被占用（Permission denied）→ 极可能有孤儿 postgres 子进程持有句柄` ✅

**处理（用户在 02:2x 授权"继续"后执行）**：
```
① 核对目标确认是孤儿（postgres.exe --forkchild="checkpointer"，父 PID 4448 已死）
② Stop-Process -Id 10848 -Force  →  已终止
③ 钩子拉起 PG → 02:22:24 就绪（等待 36.4 秒，含崩溃恢复）
④ PG 数据完好：memories 4595 / edges 46819（只增不减 ✅）
```

**三项验收（重启后，2026-10-10 02:2x）全部通过**：

| # | 验收项 | 结果 |
|:--|:--|:--|
| ① | 后端解析来源 | `backend = pg | source = backends.json[default]`，真实连接可用 ✅ |
| ② | 写入落点 | 写探针 → **落 PG**（`profile=default`）；Chroma 总数 **51396 不变**（无双写）✅ |
| ③ | 召回可读 | `get_by_id` 读回 ✅；`search_memory` 向量召回命中探针 ✅ |
| ④ | 尾部增量追平 | `pg_sync --apply`：补 4 条记忆 + 1 条边（0.4 秒）→ PG 4599 / 46820 ✅ |
| ⑤ | 探针清理 | 两条探针按 id 精确删除，残留 0 条 ✅ |

**顺带修掉一个真实缺陷（②验收时暴露）**：`pg_bridge.add_memory` 只在调用方传 timestamp 时才写 `created_at`，
否则落 NULL → **该条记忆对 `time_range` / `recent` 等时间线查询永久隐形**（库里已积累 10 条 NULL）。
已改为"缺省补当前时间"（并回写 `meta.timestamp`）。
实测：不传 timestamp 再写探针 → `created_at = 2026-10-10 02:23:35` ✅

**遗留（小）**：库里 10 条历史 `created_at=NULL` 记录，且它们的 `meta` 里也没有可用 timestamp（无法自动回填）。
影响：不会出现在时间线查询里（正常向量/关键词召回不受影响）。**待用户定：留着 or 统一补一个标记时间**。

**教训**：
- Windows 上**"隐藏控制台"≠"无控制台"**。要免疫控制台事件只能用 `DETACHED_PROCESS`（或注册成 Windows 服务）
- Windows 上**父进程死了子进程不一定死**：孤儿会继承文件句柄，把"下一次启动"彻底锁死
- 自动拉起/守护类机制的报错**绝不能丢 DEVNULL**——故障时它就是唯一线索

**操作：** fix｜**改动** `onnx_embed.py`（`_get_cached_ef()` 加双检锁）

**怎么发现的**（用户指示"你自己也切到 pg，在使用中发现问题、解决问题"）：

| 工具 | 结果 |
|:--|:--|
| `boshi_save` | ✅ 成功（写入正常） |
| `boshi_profile` | ✅ 成功 |
| **`boshi_search`** | ❌ **`cannot import name 'AutoTokenizer' from 'transformers'`** |

**根因**：`onnx_embed._get_cached_ef()` 是"惰性单例 + **无锁**"：
- **单线程**调用永远正常（我验证过 PG / Chroma 两种后端都返回 3 条）

- 这正好解释审计日志里"**save 成功、search 失败**"的错配，也很可能是 opencode 认为"记忆不可用"的直接来源

**修复**：`_get_cached_ef()` 加**双检锁**（`threading.Lock`，等锁后二次确认），并注明原因。

**验证**：**6 轮冷启动 + 并发**压测（每轮全新 MCP 进程，上来就并发 2×search + 2×save）→ **0 错误**（修复前必现）。

**清理**：删除探针/压测记录 **13 条**；PG 现状 `memories 4,584 / edges 46,788`。

⚠️ **修复需重启 MCP 进程才生效**（长活进程已加载旧代码）—— 已告知用户转告 opencode/dsh 重启其记忆连接。

## 2026-10-10 — PG 自动拉起钩子（用户选型：只做 C，不做计划任务）

**操作：** feat｜**改动** `pg_bridge.py`（+~150 行）

**用户选型**：在"Windows 服务 / 计划任务 / **数据层钩子**"三者中选 **钩子**，目标 = **任何 agent 使用伯仕时自动拉起 PG**，不做计划任务（不用 schtasks）。

**设计要点**：
1. 钩子装在 `pg_bridge.ensure_pg_running()` → 覆盖**全部入口**（Hermes 插件 / MCP server / 桥接 / CLI 都经过这一层）
2. **并发安全**：文件锁 `~/.boshi/pg_autostart.lock`（陈锁 >60s 可接管）+ 拿锁后二次确认 → 只让一方真正启动
3. **就绪等待**：轮询 `SELECT 1`（0.25s 间隔，上限 `BOSHI_PG_START_TIMEOUT=30s`）
4. ⚠️ **失败响亮报错，绝不静默退回 Chroma**（避免"一半写 PG 一半写 Chroma"的数据分叉）
5. **脱离调用方进程树**启动（`DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW`），避免 agent 进程被杀连带杀死 PG（10-09 踩过 `0xC0000142`）
6. 可配置：`BOSHI_PG_BIN` / `BOSHI_PG_DATA` / `BOSHI_PG_AUTOSTART=0`（关闭）/ `BOSHI_PG_START_TIMEOUT`
7. 过程日志：`~/.boshi/logs/pg_autostart.log`

**实测（4 项全过）**：

| 场景 | 结果 |
|:--|:--|
| 冷启动（停 PG → 任意入口访问） | 自动拉起 **≈5.0s 就绪**，检索正常 ✅ |
| 并发（3 进程同时要求拉起） | 日志精确统计 **仅 1 次真正发起启动**，其余等待共享实例 ✅ |
| 已有 PG 时额外开销 | **0.2s** ✅ |
| 关闭自启 / 拉不起来 | `RuntimeError` + 排查提示（含日志路径）✅ |
| 默认后端（Chroma）不受影响 | ✅ |

  2. `__init__()` 初始化 `_prefetch_time = 0.0`

  5. `shutdown()`：清空 `_prefetch_time`
- **修复后工作流**：
  - 第 1 轮：无缓存 → 同步搜索（慢但生效）→ 后台 queue_prefetch 更新缓存
  - 第 2 轮起：缓存命中 → 毫秒级返回 → 正常注入记忆 → 后台继续更新缓存

## 2026-09-05 — v6.4 跨话题联想召回 + 依赖问题修复

**操作：** feature + fix
**文件：**
- `plugins/boshi/__init__.py`（新增 `_expand_query_search` 方法）
- `install.py`（新增 `install_hermes_deps` 函数）

**详情：**

### 问题背景
用户反馈跨话题时记忆召回失效——谈"微调"却搜不到之前讨论的"2080Ti推理框架配置"、"vllm部署"等相关记忆。

### 根因分析
1. 查询词 = 当前消息，没有实体联想能力
2. 知识图谱 search() 方法只匹配 KNOWN_ENTITIES 静态列表，动态实体如"微调"不在列表中 → 返回空
3. 向量搜索只看当前消息语义，跨话题相似度不够，相关记忆被淹没

### 解决方案
**功能改进（v6.4）：**
- 新增 `_expand_query_search()` 方法（第307-375行）
- 从主查询结果中提取实体名（正则：大写缩写GPU、数字+字母2080Ti、驼峰命名）
- 用实体名扩展二次查询（最多3次）
- 合并主查询 + 扩展结果注入上下文

**依赖修复：**
- 发现 Hermes Gateway venv 缺少 chromadb（Hermes升级后依赖缺失）
- 修改 install.py：安装时额外安装依赖到 Hermes venv
- 新增 `install_hermes_deps()` 函数，确保插件直接可用
- 添加明确的错误提示，下次部署时自动处理
