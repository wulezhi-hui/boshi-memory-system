**1. 什么触发了这一轮：活体验证发现 P2+ 根本没生效**
开默认后拿真实 query 实跑（`scope=all`）：`field_hits` / `field_gain` **全是 None**。原因不是重排逻辑坏了，而是 `_field_match` 在 `qfields` 为空时早退——`slots.py` 的端口规则只扫「关键词**之后**」同一分句（`_ports()`，`slots.py:183-191`），人提问的写法是「8199 端口 …」（数字在前），抽不出 ports。实测 `slots.extract("8199 端口 llama-server PE 反推怎么配")` → 只有 `boundary_envs`/`statement`；`"端口 8199 监听了吗"` → `ports: ['8199']`。

**2. 为什么 A8 没抓到（方法论教训）**
A8 的 query 是「字面量 + 关键词」拼出来的，而字面量本身抄自 slot 值 → 构造上绕过了抽提器盲区。**定向验收集必须用「人真实会怎么说」写 query，不能从要验证的字段值反推。**

**3. 修法（只改 query 侧，不动文档抽提语义）**
`pg_bridge.py` 新增：

3. **成本不对称**：规则 **0.35 ms/条**（300 条实测 0.10s），4B **≈5.3 s/条**（差 1.5 万倍）；全库 1,741 条离线批 ≈ 2.4 小时独显 3060，且与 ComfyUI 抢卡。

实测否决 MiniCPM5-2.6B：F16 文件 4.7GB（比 4B Q8 的 4.3GB 还大）、硬事实全面漏（flags 命中 4/4、0/0、0/0，4B 是 6/6、16/16、15/15）、decisions 全空、是 thinking 模型（不传 `chat_template_kwargs:{"enable_thinking":false}` 会烧 700 token 在 reasoning 上、正文空）。
4B 的 `decisions` 逐字率不稳（**0/2 改写、3/3、1/3**），留着就得每条做逐字校验 —— 花代价买不确定性。

**改口条件（三条同时成立才重议混合）**：50 条对照里 `statement` 在**检索命中率**上有可测提升 ／ `decisions` 逐字率能稳到 >90% ／ 离线批时间可接受。

### 发现的真 bug（不是"首句不好"，是结构解析错）

`_sentences()` 用 `re.split('(?<=[。！？；\n])')` 之后再 `p.strip(' \t-*#>')`：

1. **strip 把 `##` 吃掉**，于是 `## 一、你问的第一件事（结论 + 已修完）` 变成「正常句子」，被当作 statement；
2. **按 `\n` 切句**，把「当前状态一句话：」和后面的正文切成两句，statement 变成这种空引子（基线 `stmt_len_avg` 只有 **38.6** 字，全库满是「两件事都有结论了。」）。

**现象**（用户重启电脑后验收时发现）：

## 2026-09-02 — v6.3 插件缓存 TTL 修复（解决 prefetch 8秒超时静默跳过）

**操作：** bug_fix
**文件：** `C:\Users\wulezhi\AppData\Local\hermes\plugins\boshi\__init__.py`
**详情：**
- **背景**：伯仕插件已注册初始化（`registered→initialized→activated`），但每轮对话前 prefetch 不召回记忆。诊断发现 Hermes v0.20.6 升级后 `_EXTERNAL_PREFETCH_TIMEOUT_S = 8.0`，伯仕 ChromaDB + ONNX bge-m3 搜索常超 8 秒，后台线程被静默跳过，且无任何超时日志
- **根因**：`prefetch()` 每轮都走同步 `_core.search()` → 慢；`queue_prefetch()` 写入缓存但 `prefetch()` 无 TTL，首轮无缓存，后续轮次缓存被超时吞掉
- **修复方案**：给缓存加 5 分钟 TTL（300秒），共改 4 处：
  1. `import time`（新增依赖）
  2. `__init__()` 初始化 `_prefetch_time = 0.0`
  3. `prefetch()`：有缓存且 `time.time() - _prefetch_time < 300` → 毫秒级返回，不触发慢搜索；无缓存/过期时同步兜底
  4. `queue_prefetch()`：后台搜索完写入 `self._prefetch_time = time.time()`；失败时清 `0.0`
  5. `shutdown()`：清空 `_prefetch_time`
- **修复后工作流**：
  - 第 1 轮：无缓存 → 同步搜索（慢但生效）→ 后台 queue_prefetch 更新缓存
  - 第 2 轮起：缓存命中 → 毫秒级返回 → 正常注入记忆 → 后台继续更新缓存
- **验证**：语法检查通过（`py_compile.compile`）；不改 Hermes 源码，升级安全
- **文档同步**：`伯仕记忆系统v6.2_技术架构文档.md` → 升级为 `v6.3`，§新增"九、prefetch 缓存机制"
- **后续注意**：若 ChromaDB 查询持续慢于 8 秒，可考虑在 `_prefetch_time` 命中时返回缓存而非空，同时 Hermes config.yaml 中 `memory.external_prefetch_timeout` 可设 30 秒作为兜底（但不推荐，会卡对话）

**文件：** dsh/boshi-auto-memory.mjs
**详情：**

## 2026-09-05 — v6.4 跨话题联想召回 + 依赖问题修复

**操作：** feature + fix
**文件：**
- `plugins/boshi/__init__.py`（新增 `_expand_query_search` 方法）
- `install.py`（新增 `install_hermes_deps` 函数）

**详情：**

### 问题背景
用户反馈跨话题时记忆召回失效——谈"微调"却搜不到之前讨论的"2080Ti推理框架配置"、"vllm部署"等相关记忆。

### 根因分析
1. 查询词 = 当前消息，没有实体联想能力
2. 知识图谱 search() 方法只匹配 KNOWN_ENTITIES 静态列表，动态实体如"微调"不在列表中 → 返回空
3. 向量搜索只看当前消息语义，跨话题相似度不够，相关记忆被淹没

### 解决方案
**功能改进（v6.4）：**
- 新增 `_expand_query_search()` 方法（第307-375行）
- 从主查询结果中提取实体名（正则：大写缩写GPU、数字+字母2080Ti、驼峰命名）
- 用实体名扩展二次查询（最多3次）
- 合并主查询 + 扩展结果注入上下文

**依赖修复：**
- 发现 Hermes Gateway venv 缺少 chromadb（Hermes升级后依赖缺失）
- 修改 install.py：安装时额外安装依赖到 Hermes venv
- 新增 `install_hermes_deps()` 函数，确保插件直接可用
- 添加明确的错误提示，下次部署时自动处理
