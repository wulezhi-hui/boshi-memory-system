## 二、问题诊断

### 2.1 现象

技术类 query 的语义召回被图谱噪声淹没，真记忆召不回：

| query | 改前召回 5 条中的噪声 |
|:-----|:-----|
| MiniMax H3 视频 | 5 条（全噪声） |
| qwen3.5 微调 | 5 条（全噪声） |
| opentelemetry 依赖 | 5 条（全噪声） |
| ComfyUI 工作流 | 4 条 |
| **合计（11 个 query / 30 条召回）** | **21 条噪声 = 70%** |

改前实测（`source="all"/"hybrid"/"vector"` 三条路都一样）：

```
qwen3.5 微调 → 5 条全是：
  Qwen3 --[derives]--> Qwen3.6-27B-AWQ [Qwen3 依赖/使用 ...]
  Qwen3.6 --[derives]--> Qwen3.8-27B AWQ [Qwen3.6 依赖 ...]
  Qwen3.6-35B --[derives]--> 能调用工具 [Qwen3.6-35B 依赖/使用 ...]
```

时间线查询同样中招：`get_time_range(近24h)` 返回的 5 条**全是** `PID xxxx --[derives]--> ...`。

### 2.2 根因分析

**知识图谱自动提边（`source=auto_extract`, `type=relation`）和真记忆混存在同一个 ChromaDB collection，参与同一套语义检索。**

L2 全库构成实测（12020 条时）：

| type | 条数 | 占比 |
|:-----|-----:|-----:|
| **relation（图谱自动提边）** | **10260** | **85.4%** |
| conversation | 782 | 6.5% |
| assistant_conclusion | 520 | 4.3% |
| session_summary | 416 | 3.5% |
| 其余（external/user/tech_config 等） | ~42 | 0.3% |

**真记忆只占约 11%**，其余 85% 是 `A --[derives]--> B` 形态的实体关系边。语义检索按相似度取 top_k，图谱边数量和占比占绝对优势，技术类 query 一旦命中实体名，前 N 名就全被边占满。

**关键点：噪声来自向量/混合检索本身（图谱边作为文档被向量化），不是图谱 BFS（`source=graph`）那一路。** 实测 `source="graph"` 对该 query 返回 0 条。

### 2.3 与 dsh 判断的对照

dsh 提出的诊断"自动召回太弱、每轮只看 3 条、应该搜 10 条截断到 3 条"——**方向对但归因和药方偏**：

| dsh 说法 | 判定 | 依据 |
|:-----|:-----|:-----|
| 自动召回碎片化 | ✅ 对 | 85% 噪声实测支持 |
| 搜 3 条太少 → 应该搜 10 条 | ❌ 药方错 | 库里 85% 是噪声时，搜 10 条只会捞回更多噪声；Hermes 插件侧本来就是 top_k=5 + 历史FTS + 实体扩展（注入 8~10 行），照样 70% 噪声 |
| 相对时间词理解不了 | ✅ 对 | 但这是**独立问题**，与噪声无关 |
| 加 boshi_timeline 工具 | 🔸 部分 | `boshi_time_range` 已存在（dsh 自己加的），但同样没过滤噪声 |

**结论：dsh 的"条数论"不成立，真正病根是数据层的图谱边污染检索。**

## 三、解决方案

### 3.1 核心思路

在**数据层**（`chroma_bridge`）默认隔离图谱边，而不是在消费侧各自打补丁：

```
改前：检索 ↔ [真记忆 11% + 图谱边 85%]  → 噪声按相似度挤占 top_k
改后：检索 ↔ [真记忆 11%]                → 干净召回（图谱边仍可按需 include_graph=True 取回）
```

理由：
1. **一处改、全链路受益**：Hermes 插件、dsh 桥接、MCP 工具、CLI 全部走 `boshi_core.search` → `chroma_bridge`，改底层一次性治好
2. **图谱能力不丢**：图谱模块自身用 `where={"type": "relation"}` 显式检索（`knowledge_graph.py` 5 处），`_where_has_type()` 白名单自动放行，不被误伤
3. **保留按需召回**：需要图谱联想时 `include_graph=True`

### 3.2 实现细节

**新增两个辅助函数**（`chroma_bridge.py`）：

```python
def _where_has_type(where: dict) -> bool:
    """调用方是否显式指定了 type 条件（图谱模块查 relation 时用）"""

def _apply_graph_exclusion(where: dict, include_graph: bool) -> dict:
    """默认排除 type=relation；两种情况放行：
       1. 显式 include_graph=True
       2. 调用方自带 type 条件（图谱模块自身检索）
       返回新 dict，不改调用方传入的 where"""
    where = dict(where) if where else None
    if where and "$and" in where:
        where = {"$and": [dict(c) for c in where["$and"]]}   # 防别名污染
    if include_graph or (where and _where_has_type(where)):
        return where
    cond = {"type": {"$ne": "relation"}}
    if not where:
        return cond
    if "$and" in where:
        return {"$and": [dict(c) for c in where["$and"]] + [cond]}
    return {"$and": [where, cond]}
```

**统一 where 匹配函数**（退化路径用，替换原来只认 `type` 相等的简化逻辑）：

```python
def _cond_matches(meta, cond) -> bool:   # 支持 {k: v} 与 $ne/$gte/$lte
def _where_matches(meta, where) -> bool: # 支持 $and 组合
```

**改动点清单**：

| 文件 | 位置 | 改动 |
|:-----|:-----|:-----|
| `chroma_bridge.py` | 新增 | `_where_has_type` / `_apply_graph_exclusion` / `_cond_matches` / `_where_matches` |
| `chroma_bridge.py` | `search_memory()` | 加 `include_graph: bool = False`；调用 `_apply_graph_exclusion` |
| `chroma_bridge.py` | `search_memory()` 退化分支 | Python 端过滤改用 `_where_matches` |
| `chroma_bridge.py` | `hybrid_search()` | 加 `include_graph` 透传 |
| `chroma_bridge.py` | `get_time_range()` | 加 `include_graph`；where 加排除；退化分支改用 `_where_matches` |
| `boshi_core.py` | `search()` | 加 `include_graph`，透传给 `search_memory`/`hybrid_search` |
| `boshi_core.py` | `time_range()` | 加 `include_graph` 透传 |
| `boshi_mcp_server.py` | `boshi_search` / `boshi_time_range` | 加 `include_graph` 参数 + 描述；修 docstring 8→9 |

### 3.3 设计权衡

| 选择 | 理由 | 代价 |
|:-----|:-----|:-----|
| 默认排除（而非默认包含） | 85% 是噪声，默认干净才符合直觉 | 需要图谱联想时须显式传 `include_graph=True` |
| 用 `type != relation` 而非 `source != auto_extract` | `type` 是图谱模块既有的判定字段，语义稳定 | 手工添加的 relation 同样被排除（当前无此场景） |
| 在数据层过滤而非消费侧 | 一处改全链路受益，避免 dsh/Hermes 两边逻辑不一致 | 底层改动的回归面较大（已全量回归） |
| `_where_has_type` 白名单放行 | 图谱模块 5 处显式查 relation，硬排除会打断图谱功能 | 略增判断分支 |
| 删除图谱边？ | **不做**——图谱功能本身有效，只是不该挤占召回名额 | — |

### 4.3 已知限制

1. **图谱边仍在库里占 85% 存储**：本次只做检索隔离，未做数据清理。若后续要减体积，可考虑迁移到独立 collection
2. **`get_recent()` 未同步过滤**：它用 `col.get(limit=n)` 取前 n 条（另一处独立问题——"最前"不是"最新"），本次未动
3. **`profile()` 的 hot_topic 变空**：热区检索用 `heat>=10`，而 `heat` 字段**只存在于图谱边**（非图谱记忆实测 0 条带 heat）→ 改后 hot_topic 由图谱噪声变为空字符串。**这是修正而非退化**：消费方（Hermes 插件/dsh）本来就有 `isGraphNoise` 过滤把这类边滤掉，无感

## 六、技术要点

### 6.1 与 v6.4 的关系

v6.4 解决"跨话题召回断联"（扩展查询），v6.5 解决"召回被图谱边挤占"。两者互补：
- v6.4 让召回**更广**（实体扩展）
- v6.5 让召回**更准**（噪声隔离）

**注意**：v6.4 的 `_expand_query_search()` 提取实体名后调 `self._core.search(entity, top_k=2, source="vector")`，该路径自动继承 v6.5 的过滤，扩展召回质量同步改善。

### 6.2 与知识图谱的关系

图谱双存储结构（`knowledge_graph.json` 节点边 + ChromaDB 的 relation 文档）不变。本次只影响**ChromaDB 侧 relation 文档是否参与通用召回**：

| 使用方 | 改前 | 改后 |
|:-----|:-----|:-----|
| 通用召回（search/time_range） | 边混入，噪声 70% | 默认排除 |
| 图谱模块（显式 `type=relation`） | 正常 | 正常（白名单放行） |
| `include_graph=True` | — | 可显式取回边 |

### 6.3 性能影响

- 检索侧：`where` 多一个 `$ne` 条件，ChromaDB 原生支持，无额外开销；反而因过滤后候选集变小、Python 端排序更轻
- 存储侧：无变化（未删数据）

## 七、总结

| 项 | 内容 |
|:-----|:-----|
| 问题 | 图谱自动提边占库 85%，混入语义召回，技术类 query 噪声率 70% |
| 根因 | 图谱边与真记忆同 collection、同检索路径 |
| 方案 | 数据层默认隔离 `type=relation`，`include_graph` 开关按需放行 |
| 效果 | 噪声 70% → 0%；图谱功能与数据完整性均无损 |
| 影响面 | Hermes 插件、dsh 桥接、MCP 工具、CLI（一次改动全链路生效） |
| 遗留 | 图谱边仍占 85% 存储；`get_recent` 未同步处理 |
