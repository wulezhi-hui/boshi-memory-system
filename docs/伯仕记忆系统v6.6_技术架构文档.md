## 二、问题与设计

### 2.1 问题

四个 profile（default / dashi / shizhen / zuojia）加上通过 MCP 接入的 dsh，**共享同一份 ChromaDB**。不隔离会导致：

- 人格互串：写小说时召回中医辨证记忆，反之亦然
- 无法区分来源：不知道某条记忆是哪个入口写的

### 2.2 设计（用户定稿）

> "不同 profile 使用同一个数据库，但记忆应加上各自的标识；读取时通常只读自己标识的部分，除非要求读取其它 profile 才读全部，包括通过 MCP 接入的其它 agent 的记忆——可以切换全库检索和只检索自己。"

三条决策：

1. **老数据**：统一归 `default`（而非"视作缺字段"——用真实回填，避免依赖 ChromaDB 的缺失字段语义）
2. **图谱边**（`type=relation`）：**不打标识**，保持全局知识网络（跨领域关系边与人格无关）
3. **默认范围**：`self`（只读自己的）

### 2.3 归属标识的解析

```python
resolve_profile():  BOSHI_PROFILE 环境变量 > HERMES_HOME 推导 > "default"
```

| 写入方 | 标识来源 | 值 |
|:-----|:-----|:-----|
| Hermes 各 profile 插件 | `get_hermes_home()` 推导，并 `setdefault` 到 `BOSHI_PROFILE` | `default` / `dashi` / `shizhen` / `zuojia` |
| DSH 插件 / MCP | `cordis.patch.yml` 的 `env.BOSHI_PROFILE` | `dsh` |
| CLI / 桥接 | `BOSHI_PROFILE` 环境变量，或 `--profile=` 显式指定 | 任意 |

## 三、实现

### 3.1 数据层（`chroma_bridge.py`）

```python
# 写入：非图谱记录自动打标
if meta.get("type") != "relation":
    meta.setdefault("profile", resolve_profile())

# 检索：归属过滤（与 v6.5 的图谱排除叠加）
def _apply_profile_scope(where, scope, me):
    if scope in ("all", "*"): return where          # 全库
    cond = {"$or": [{"profile": me}, {"type": "relation"}]}  # 自己的 + 全局图谱边
    ...merge into where...
```

- 图谱边在 `$or` 中放行 → `include_graph=True` 时不会被归属过滤挡掉
- 调用方自带 `profile` 条件时尊重调用方，不叠加
- 返回新 dict，不污染调用方传入的 `where`（沿用 v6.5 的别名防护）
- Python 退化路径 `_cond_matches()` 增加 `$or` 支持

### 3.2 版本链

`deprecate_memory` 本就读旧 metadata 后回写（标识天然保留）；`update_memory` 新增**继承旧版本 `profile`**，避免从别的 profile 进程更新时把标识改写。

### 3.3 读路径矩阵

| 读路径 | 参数 | 默认 | 说明 |
|:-----|:-----|:-----|:-----|
| `search_memory` / `hybrid_search` | `scope`, `me` | profiles.json → `self` | 语义/混合检索 |
| `get_time_range` | `scope` | 同上 | 时间线 |
| `get_recent` | `scope` | 同上 | 顺带补上 where 过滤（原本无任何过滤） |
| `profile()` | `scope` | 同上 | 热区 + 近期 |

### 3.4 配置开关

`~/.boshi/profiles.json`：

改 `"all"` 即该入口默认全库检索（读取时实时生效，无需重启）。

### 3.5 通用 MCP 接口：调用方身份自动识别（v6.6 补）

**设计意图（用户定稿）**：伯仕侧提供**通用 MCP 接口**，任何 agent 直接调用即可；**读写时伯仕自动带上调用方自己的标识——接入方无需任何配置**。

实现：MCP 2.0 允许工具函数声明 `Context` 类型参数，框架自动注入握手上下文（不上传给模型）。据此从 `ctx.session.client_params.clientInfo.name` 取调用方名称：

```python
def _caller_identity(ctx) -> Optional[str]:
    """优先级（MCP 握手是"谁在调用"最具体的信号，优先于环境变量）：
      1. BOSHI_PROFILE 环境变量（接入方显式配置）
      2. MCP 握手 clientInfo.name（零配置自动识别）
      3. 若设了 HERMES_HOME → None（交下游按 profile 解析；仅用于无客户端名的 Hermes 自带 MCP）
      4. 兜底 "external"（不落 default，避免污染主身记忆空间）
    """
```

> ⚠️ **2026-09-15 实测修正**：初版把"设了 HERMES_HOME 就当作 Hermes 在调用"放在 clientInfo 之前，
> 结果**外部 agent 全部被误判**——因为 `HERMES_HOME` 被写进了**用户级 Windows 环境变量**
> （`HKCU\Environment`），opencode 启动时一并继承 → 其写入被归到 HERMES_HOME 派生的 `default`。
> **修正：MCP 握手（具体信号）优先于环境变量（环境噪音）。**

### 3.7 MCP 调用审计日志

`~/.boshi/logs/mcp_calls.jsonl`（每次调用追加一行 JSONL，失败静默不影响主流程）：

```json
{"ts":"2026-09-15T10:34:00","identity":"opencode","client":"opencode","tool":"boshi_save",
 "scope":"写入(归属自动打标)","env_HERMES_HOME":true,"query":"…"}
{"ts":"2026-09-15T10:34:07","identity":"opencode","client":"opencode","tool":"boshi_search",
 "scope":"(未传→默认 self)","env_HERMES_HOME":true,"query":"…"}
```

字段：`identity`（最终归属）、`client`（握手自报名，用于诊断）、`tool`、`scope`（**未传会明确标注**）、
`env_*`（是否受环境变量影响）、`query`。

**用途**：把"模型到底传没传 `scope=all`""识别成了谁"从**推测**变成**可查的事实**——本次就是这样定位到优先级 bug 的。

标识规整：小写、非 `[0-9A-Za-z._-]` 字符转 `-`、限长 32。

读写两侧都用它：
- **写**：`boshi_save` → `save(profile=_caller_identity(ctx))`
- **读**：`boshi_search`/`time_range`/`recent`/`profile` → `me=_caller_identity(ctx)`

**显式传参而非改进程环境变量**：MCP 进程可能被多客户端共用（HTTP 模式），故 `boshi_core` 的读函数新增 `me` 参数显式透传，避免依赖 `os.environ` 造成串号。

### 3.6 接口自述：把约定讲给接入方（而非逐家适配）

**设计意图（用户定稿）**：不要在**各自 agent 侧**分别设置，而是**让通用接口自己声明这套设定**，任何 agent 接进来就懂。

两个自述渠道：

| 渠道 | 机制 | 特点 |
|:-----|:-----|:-----|
| **① `initialize.instructions`** | `MCPServer(..., instructions=SERVER_INSTRUCTIONS)`，随握手返回 | 一次性告诉客户端全套约定（身份/写入打标/scope 语义/图谱开关）；**是否注入模型上下文取决于客户端** |
| **② 响应内联字段** | 每次调用的返回里带 `_identity` / `_scope` | 模型**每次调用都能看见**"我是谁、这次生效范围"；默认 scope 时值写成 `self(默认，全库请传 scope=all)`——**在带内把开关教给模型** |

自述内容（`SERVER_INSTRUCTIONS`）要点：

1. 身份由伯仕按 MCP 握手自动识别（= 客户端名）
2. 写入自动打标，无需传参
3. 读取默认只读自己的；要全库传 `scope="all"`
4. 返回结果的 `_identity`/`_scope` 反映当前身份与范围
5. 图谱边全局共享，需 `include_graph=true`
6. 用户说"查其它 agent / 全部 / 全局记忆"时 → `scope="all"`

**兼容性**：`_with_meta()` 只对 **dict** 结果补字段；`time_range`/`recent` 是 list，保持原样（dsh 插件用 `Array.isArray` 判定格式，不能改）。

### 3.8 向量模型与重排：加载策略（2026-09-18 补档）

**一句话**：每个进程持有自己的 bge-m3 ONNX 会话——**惰性加载、进程内永驻、无卸载机制**；当前管线**没有重排序模型**；"是否常驻"取决于**宿主进程寿命**，与模型自身无关。

#### (1) 向量模型：读写双向必经

| 操作 | 模型调用 |
|:-----|:-----|
| 写入 `add_memory()` | ChromaDB `embedding_function` 对**正文**编码 → 存 1024 维向量 |
| 检索 `search_memory()` | 对**查询词**编码 → HNSW 近邻 |

实现：`~/.boshi/onnx_embed.py` —— **onnxruntime CPU** + transformers tokenizer，模型 `~/.boshi/models/bge-m3/onnx/model_quantized.onnx`（int8，544MB，1024 维）。
**不依赖**：Ollama、torch、sentence-transformers、在线推理、外网。

#### (2) 加载 / 卸载

```python
# onnx_embed.py:62
_boshi_ef_instance = None                  # 模块级单例
def _get_cached_ef():
    global _boshi_ef_instance
    if _boshi_ef_instance is None:         # ← 首次实际使用才加载（tokenizer + InferenceSession）
        ...
    return _boshi_ef_instance
```

- **加载时机**：首次**实际调用**（不是 import 时）→ 表现为"第一轮召回慢，之后快"
- **卸载**：代码中**不存在任何 TTL / unload / evict 路径** → 进程内永驻，只能靠进程退出释放
- **内存占用**：模型 544MB（磁盘）→ 实测驻留进程 1692MB（含 ChromaDB + Hermes 运行时）

#### (3) 宿主进程决定生命周期

| 入口 | 宿主进程模型 | 模型生命周期 | 单次代价 |
|:-----|:-----|:-----|:-----|
| **Hermes 插件**（default/dashi/shizhen/zuojia） | gateway worker **常驻** | 首次召回加载 → **进程内常驻** | 首次 8.5s，之后 0.12s |
| **MCP**（dsh / opencode） | stdio **长连接**子进程 | 连接存续期间**常驻**；客户端断开即随进程释放 | 首次同上 |
| **CLI / `boshi_bridge.py`** | **每次调用 spawn 新进程** | **每次冷启动**，退出即释放 | **15.74s / 次** |

#### (4) 重排模型：未接入（三条证据）

| 证据 | 结果 |
|:-----|:-----|
| 代码检索 `rerank` / `CrossEncoder` / `FlagReranker` / `sentence_transformers` | 仅命中**死代码** `~/.boshi/memory/chroma_memory.py:56`（无人 import）；`chroma_bridge.py` 等主链 0 引用 |
| venv 依赖 | 只有 `onnxruntime 1.28.0`，**无** torch / sentence-transformers / FlagEmbedding |
| 磁盘权重 | `~/.boshi/models/`、`~/.cache/huggingface/` 下**无** reranker 文件 |

因此三路融合的排序依据是 **向量相似度降序 + `content[:50]` 去重**，**没有 cross-encoder 精排层**。召回提纯当前靠结构性过滤：排图谱边（`type != relation`）+ 归属（`scope`）+ `isLatest`，实测噪声率 70% → 0。

### 4.4 冷热启动与进程驻留实测（2026-09-18）

**耗时实测**（`~/.boshi/venv` python，Windows，同一台机）：

| 场景 | 实测 |
|:-----|:-----|
| 同进程**首次** `search_memory()`（模块 import 2.16s + 加载 ONNX + ChromaDB 建索引 + 首次推理） | **8.52 s** |
| 同进程第 2 次 `search_memory()` | **0.12 s** |
| 同进程第 3 次 `search_memory()` | **0.12 s** |
| `boshi_bridge.py search ...`（**每次新进程**，dsh 插件走这条） | **15.74 s / 次** |

**进程级驻留证据**（查进程内是否加载了 onnxruntime，非推断）：

| 进程 | 内存 | onnxruntime 加载 |
|:-----|:-----|:-----|
| default profile 的 agent worker（`hermes_bridge.py --worker-profile default`） | **1692 MB** | ✅ `onnxruntime_pybind11_state.pyd`(18MB) + `tokenizers.pyd`(8MB) |
| 另一 worker（未触发过任何召回） | 186 MB | ❌ 未加载 |

→ 双向印证：**已用过召回的进程把模型驻留在内存里；没用过的进程不含模型**（懒加载成立）。

**推论 1（设计必要性）**：Hermes 插件的"后台 `queue_prefetch` + 300s 缓存"是**必需**而非优化——冷启动 8.52 s **已超过** Hermes 对外部 provider 的超时门 `_EXTERNAL_PREFETCH_TIMEOUT_S = 8.0`（`hermes-agent/agent/memory_manager.py:32`）。若不预热，首轮召回会被静默跳过（且该 provider 在卡住调用返回前会被持续跳过）。

**推论 2（性能弱环）**：dsh 桥接路径每轮付 **15.74 s** 冷启动（见 §6.5）。

## 六、已知限制与后续

1. **老数据归属**：2073 条历史记录统一归 `default`（含 dsh 历史写入）。若要精确回填，需用 `session_id` 对照各 profile `state.db` 反推（未做）
2. **`get_recent` 排序**：仍按 ChromaDB 内部顺序取，非时间倒序（历史遗留，本次只叠加过滤）
3. **临时文件**：`profiles.json` 若损坏 → `load_profile_config()` 静默降级为全 `self`，不影响可用性
4. **生效条件**：Hermes 各 profile 网关需重启以加载新插件与核心代码（进程内模块缓存）
5. **dsh 桥接冷启动开销**（2026-09-18 实测）：`boshi_bridge.py` 每次调用都是**新进程** → 单次约 **15.74 s**（模型冷加载），dsh 插件每轮调用一次即为每轮固定开销。可选改进（未做）：① 让 dsh 只走 MCP（连接级复用，模型随连接常驻）；② 桥接改**常驻守护进程**（socket/HTTP），插件连它而非每次拉起
6. **无重排层**：当前排序 = 向量相似度降序 + `content[:50]` 去重，**未接 cross-encoder**。若加：需引入 torch（~2GB 依赖），CPU 上重排 top-20 约 +0.3~1 s。当前靠结构性过滤（排图谱边 + 归属 + `isLatest`）已把噪声率压到 0，暂不引入
7. **MCP 连接与代码版本**：`boshi_mcp_server.py` 是**长驻子进程**，改动代码后**已建立的连接仍跑旧代码**，必须让接入方**重连**（重启该 agent/会话）才生效。诊断：比对进程 `CreationDate` 与文件 mtime（2026-09-15 现场：opencode 旧连接导致写入误落 `default`）
